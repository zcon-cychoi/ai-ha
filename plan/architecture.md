# AI-HA 아키텍처

AI-MCMP의 **AI반도체 서비스의 클라우드간 고가용성 제공 프레임워크(AI-HA)** 중
백업/복구 영역의 목표 구조와 역할 분담을 정의한다.

관련 문서: [backup.md](backup.md) (백업 방식), [Restore.md](Restore.md) (복구 시퀀스),
[protocol.md](protocol.md) (통신 규약), [data-model.md](data-model.md) (도메인 모델),
[open-decisions.md](open-decisions.md) (미결정 사항)

## 1. 구성 요소

AI-HA는 **프레임워크 서버 1개**와 **대상 VM마다 하나씩 동작하는 에이전트 N개**로 구성된다.

```
                          AI-MCMP 플랫폼
   ┌──────────────────────────────────────────────────────┐
   │  개방형 API (Facade) / 통합 포털 (One GUI)             │
   └───────────────────────┬──────────────────────────────┘
                           │ 북향 REST API (Swagger 2.0)
                           ▼
   ┌──────────────────────────────────────────────────────┐
   │  AI-HA 프레임워크 (aiha-framework)                     │
   │   · 보호 대상 등록/조회                                │
   │   · 백업/복구 잡 생성 · 작업큐 · 상태머신               │
   │   · 진행 상태 추적, 수행 결과/이력 관리 (정본 DB)        │
   │   · 복구 플랜 수립, 복구ID 발급, 저장소 접속정보 중개     │
   └───────┬──────────────────────────────┬───────────────┘
           │ 남향: 롱폴링 작업큐            │ 인프라 제어 API 호출
           │ (에이전트 발신 아웃바운드)      │ (복구용 인스턴스 생성)
           ▼                              ▼
   ┌───────────────────┐        ┌─────────────────────────┐
   │ aiha-agent        │        │ AI-MCMP 인프라 연동/     │
   │  (대상 VM / 레스큐) │        │ 통합 관리 프레임워크      │
   │  · 백업 수행       │        └─────────────────────────┘
   │  · 복구 수행       │
   └────────┬──────────┘
            │ 백업 데이터 실시간 스트림
            ▼
   ┌──────────────────────────────────────────────────────┐
   │  백업 저장소 (local / sftp / smb / s3 / http)          │
   │   · 시스템별 디렉터리 + 백업 파일(.aha)                 │
   │   · 세트별 manifest.json (복구 정본) + SQLite 색인       │
   └──────────────────────────────────────────────────────┘
```

### 1.1 역할 경계

| | 프레임워크 (`aiha-framework`) | 에이전트 (`aiha-agent`) |
| --- | --- | --- |
| 배치 위치 | AI-MCMP 중앙 통합 관리 | 백업 대상 VM / 복구용 레스큐 인스턴스 |
| 명령 | 발행한다 | 수신해서 수행한다 |
| 백업 데이터 | **경유하지 않는다** | 저장소로 직접 스트리밍한다 |
| 저장소 자격증명 | 보관하고 필요 시 중개한다 (현재: 등록된 키를 암호화 보관, 잡 claim 응답에서만 복호화) | 잡 수행 중에만 전달받아 사용한다 |
| 이력/진행 상태 | 정본을 보유한다 | 보고만 한다 |
| 외부 API | 북향 REST 제공 + 인프라 API 소비 | 없음 (아웃바운드 호출만) |

**핵심 원칙: 백업 데이터는 프레임워크를 경유하지 않는다.**
프레임워크는 제어 평면(control plane)이고, 실제 바이트는 에이전트 → 저장소로 직접
흐른다. 프레임워크가 데이터 경로에 끼면 중앙 서버가 전체 대역폭의 병목이자 단일
장애점이 되므로, 명령·상태·이력만 다룬다.

### 1.2 용어: "에이전트"의 중의성

연구과제 문서(`docs/req.docx`)에서 **"에이전트"는 LLM/AI 에이전트를 뜻한다.**

- SFR-API-04 "MCP like API(MCP Gateway)" — AI 에이전트가 플랫폼 기능을 MCP 도구로 호출
- 6.5절 "AI 서비스 HA 지원 에이전트 기술" — AIOps 프레임워크 소속, 경희대학교산학협력단 담당
- 시나리오 OPS-01/02의 "AI 에이전트 등록·권한·라이프사이클"

이는 **본 문서의 백업 노드 에이전트와 전혀 다른 개념이다.** 연구과제 산출물 문서에서
수식어 없이 "에이전트"라고 쓰면 리뷰어가 혼동하므로, 아래 표기를 사용한다.

- 코드/바이너리: `aiha-agent`
- 국문 서술: **백업 노드 에이전트** 또는 **AI-HA 에이전트**
- 연구과제 문서의 AI 에이전트를 가리킬 때만 "AI 에이전트"

## 2. 현행 코드의 위치 (2026-10-13 기준)

`aiha-agent`·`aiha-framework` CLI는 사용자용 인터페이스가 아니라 운영·검증용 진입점이다. 실제
사용자는 AI-MCMP 포털이나 개방형 API를 통해 AI-HA를 쓴다 — 그 북향 API는 2026-11-03에 틀을 세웠고,
구현된 기능은 동작한다 ([protocol.md](protocol.md) 4.1). CLI는 아직 DB에 직접 붙는다(2.1).

**에이전트**

| --- | --- |

| `pkg/backup/archive/` | tar 아카이빙/추출 |

| `pkg/backup/meta/` | 시스템별 SQLite 색인 (매니페스트로 재생성 가능) |

레스큐 빌드에는 미링크), `pkg/filelock/`, `pkg/logging/`.

### 2.1 아직 없는 것

- **북향 API의 501 경로** — 재수집, 백업 대상 등록, 백업 삭제, 복구 취소, 저장소 검증, 이중화,
  장애 이력 ([protocol.md](protocol.md) 4.1). `Idempotency-Key`도 없다 (4.3)
- **CLI의 북향 경유** — CLI는 여전히 DB에 직접 붙는다. TM-AI-HA-03은 CLI까지 북향 API로 처리하는
  것을 후속으로 둔다
- 백업 세트 카탈로그 — 이력은 잡 기록에서 읽으므로, 저장소에 실제로 있는 세트는 알지 못한다
- 인프라 프레임워크를 호출한 복구용 인스턴스 생성 (`InfraProvisioner`) — 지금은 aiha-init.sh 값으로 수동 생성
- 부팅 확인(boot-verify)과 복구된 시스템의 재등록 — 그 전까지 복구된 시스템은 다시 백업할 수 없다
- 단기 자격증명(STS)·복구 전용 읽기 키, 저장소 삭제·접속 검증
- `restoring` 잡 타임아웃 스위퍼, 복구 후 자동 재부팅·체크섬 검증
- 일반화된 복구(파티션 테이블 복구, LVM, 다른 이미지) — 1차년도는 같은 AMI 전제 ([Restore.md](Restore.md) 3.8)
- 이중화의 복제 상태 수집(DRBD), 복제 구성·전환 잡 — [ha-roadmap.md](ha-roadmap.md) H0 이후. 헬스 보고·판정(H1)은
  있고, 북향 `/aiha/ha/*`는 501이다(1차년도 프로토타입은 CLI)

`pkg/backup/engine`의 `Restore`(`aiha-agent extract`)는 여전히 아카이브를 디렉터리로 푸는 수준이고,
실제 시스템 복구는 `pkg/agent/restore`가 레스큐에서 한다.

## 3. 바이너리 구성

**소스는 `aiha-framework` / `aiha-agent` 2개, 빌드 산출물은 3개**다. `aiha-backup`
CLI는 `aiha-agent`로 흡수했고([open-decisions.md](open-decisions.md) 7번 — 해소),
레스큐용 경량 빌드는 같은 소스에 빌드 태그를 걸어 만든다.

| | `aiha-framework` | `aiha-agent` | `aiha-rescue` |
| --- | --- | --- | --- |
| 빌드 | `./aiha-framework` | `./aiha-agent` | `./aiha-agent` + `-tags rescue` |
| 실행 위치 | 중앙 관리 서버 (상시 구동) | 대상 VM | system-rescue 환경 |
| 의존성 | Echo, pgx (인프라 API 클라이언트는 아직 없음) | 저장소 백엔드, 아카이버, 코덱, SQLite, HTTP 클라이언트 | HTTP 클라이언트, 외부 도구(rclone·mkfs·tar 등) 호출 |
| 사용 패키지 | `pkg/framework/*`, `pkg/api/rest/` | `pkg/backup/*`, `pkg/agent/*` | `pkg/agent/rescue`, `pkg/agent/restore` (+ `pkg/backup/model`·`sysinfo`) |
| 크기 (참고, 2026-10-13) | ~32 MB | ~23 MB | **~12 MB** |

**레스큐 빌드를 나눈 이유**: 복구 시 에이전트는 EC2 user-data에서 내려받아
system-rescue 환경에 올려야 한다([Restore.md](Restore.md) Mode A). `copytoram`으로
RAM에 상주하므로 크기가 그대로 메모리 점유가 된다. 전체 빌드에는 minio-go,
go-smb2(+gokrb3 스택), pkg/sftp, `modernc.org/sqlite`, Echo, pgx가 링크되는데
**복구 경로는 그중 무엇도 쓰지 않는다** — [roadmap.md](roadmap.md) Phase 2에서 복구
읽기를 rclone으로 하기로 했기 때문이다. 태그로 걷어내면 복구 실행기를 포함해도 252개 패키지(약 12 MB)만
남는다(복구 실행기가 들어가기 전에는 246개, 7.5 MB).

**최소 권한도 같은 빌드로 해결된다**: `config/`가 `AIHA_BACKUP_*` 하나로 양쪽 설정을
담고 있어, 프레임워크 접속 정보만 필요한 레스큐 에이전트가 저장소 자격증명까지
읽는 구조였다. 레스큐 빌드는 `config` 패키지를 **링크조차 하지 않으므로** 규약이
아니라 링커가 이를 보장한다. 전체 빌드에서도 설정 로딩을 루트의
`PersistentPreRunE`에서 각 커맨드의 `PreRunE`로 내려, `rescue` 서브커맨드는 저장소
자격증명을 읽지 않는다.

## 4. 외부 인터페이스

AI-HA 프레임워크는 API를 **제공하는 동시에 소비한다.**

### 4.1 북향 API — 제공 (연구과제 요구사항)

SFR-API-02는 "OpenAPI 3.0 기반 개방형 API(Facade) 및 통합 포털(One GUI)"을
요구한다(베스핀글로벌, 2028). 시나리오 APP-03에 따르면 개방형 API는
**"AI-MCMP의 모든 기능에 대해 API를 통합하는 Façade 패턴"** 이다.

따라서 각 프레임워크는 이 Façade에 통합될 **북향 REST API**를 제공해야 하며,
연구과제가 AI-HA에 요구하는 API는 바로 이것이다.

API 문서는 `swag`가 만드는 **Swagger 2.0**으로 제공한다. 요구사항 문구와 베스핀글로벌은 OpenAPI
3.0을 언급했지만, 주관기관 ETRI가 Swagger 중심으로 간다고 해 별도 지시가 있을 때까지 Swagger를
유지한다 (2026-11-03).

### 4.2 남향 프로토콜 — 규정 없음

**프레임워크↔에이전트 구간에 대한 규정은 연구과제 문서 어디에도 없다.**
SFR-HA-01~03, UFR-HA-01/02, 시나리오 HA-09/HA-10 전부 "AI-HA 프레임워크가
백업/복구를 수행하고 상태를 제공한다"까지만 기술하며, 내부 구현 방식은 제약하지
않는다. 따라서 **자유 선택**이며, 본 프로젝트는 롱폴링 작업큐를 채택한다
(근거는 [protocol.md](protocol.md) 1절).

### 4.3 인프라 제어 API — 소비

복구 시 대상 인스턴스 생성([Restore.md](Restore.md) Mode A)은 AI-HA가 직접 하지
않고, **AI반도체 클라우드 인프라 연동/통합 관리 프레임워크의 추상화 API**를
호출해야 한다.

> SFR-CON-02: 서로 다른 AI반도체 클라우드 인프라를 연동 및 제어 가능한 추상화된
> API를 제공해야 한다. (한국전자통신연구원, 2026)

이 API는 아직 사용할 수 없으므로, AI-HA 내부에 `InfraProvisioner` 형태의 **좁은
인터페이스**를 두어 격리한다. 필요한 동작은 다음 정도로 한정된다.

- 지정 사양으로 인스턴스 생성 (초기화 스크립트 = EC2 user-data 주입 포함)
- 인스턴스 상태 조회
- 인스턴스 종료

구현체 선택(당장 AWS 직결 / 인프라 프레임워크 대기)은
[open-decisions.md](open-decisions.md) 2번.

### 5.2 협력 범위 — 마이그레이션 (SFR-HA-08~14)

연구과제 문서상 담당기관은 한국전자통신연구원이지만, **실제로는 제트컨버터클라우드가
협력하기로 합의된 상태다.** 다만 협력 방식은 아직 결정되지 않았다.

| 요구사항 ID | 내용 | 시기 |
| --- | --- | --- |
| SFR-HA-08 | 소스 환경의 AI 서비스 실행 인프라(VM, 컨테이너) 조회 및 분석 | 2027 |
| SFR-HA-09 | 목표 클라우드에 대한 실행 인프라 추천, 마이그레이션 실행 및 검증 | 2027 |
| SFR-HA-10 | 소스 환경의 AI 모델/응용 구성 정보 수집 및 분석 | 2028 |
| SFR-HA-11 | 모델/응용 구동환경 변환·최적화, 마이그레이션 실행 및 검증 | 2028 |
| SFR-HA-12 | 소스 환경의 AI 서비스 운용 데이터 조회 및 분석 | 2029 |
| SFR-HA-13 | 데이터 마이그레이션 방식 추천/도출, 실행 및 검증 | 2029 |

미결정된 협력 방식 ([open-decisions.md](open-decisions.md) 9번):

1. **ETRI 방식 기반** — ETRI 설계를 베이스로 우리가 보조
2. **우리 방식 기반** — AI-HA 백업/복구 엔진을 베이스로 ETRI가 보조
3. **2-way** — 양쪽을 병행

**설계상 함의 — 지금 결정해 둬야 하는 이유**:
마이그레이션은 기계적으로 *소스에서 백업 → 목표 클라우드에 복구*와 상당 부분
겹친다. 특히 [Restore.md](Restore.md)의 **Mode A(신규 인스턴스 복구)는 목표
클라우드에 새 인스턴스를 만들어 그 안으로 복구하는 것**이므로, 소스와 목표가 다른
클라우드이기만 하면 그것이 곧 SFR-HA-09의 인프라 마이그레이션이다.

따라서 2안 또는 3안이 채택될 경우 지금 만드는 백업/복구 경로가 마이그레이션의
기반이 된다. 방식이 확정되기 전이라도 아래는 지켜서 어느 안이든 수용 가능하게 한다.

- **소스 시스템과 복구 대상 환경을 분리된 개념으로 모델링한다.** 복구 잡이 "원래
  있던 자리로 되돌린다"를 전제하지 않는다. 목표 클라우드/리전/사양을 복구 잡의
  파라미터로 둔다.
- **잡 종류를 구분하는 필드를 이력 스키마에 둔다.** 나중에 `migration` 잡 종류가
  추가되어도 스키마 변경 없이 SFR-HA-07(이력 통합 관리)을 만족할 수 있게 한다.
- **`InfraProvisioner` 인터페이스를 클라우드 중립으로 유지한다.** AWS 전용 개념이
  인터페이스에 새어 나오지 않게 한다.

## 6. 설계 원칙

1. **제어 평면과 데이터 평면 분리** — 프레임워크는 명령·상태·이력만, 백업 바이트는
   에이전트↔저장소 직결.
2. **에이전트 발신 아웃바운드 통신** — 대상 VM에 인바운드 포트를 열지 않는다.
   멀티 클라우드·NAT·레스큐 환경 어디서나 동작하고, 백업과 복구가 같은 방향이 된다.
3. **잡은 이벤트가 아니라 상태** — 모든 잡은 프레임워크 DB에 영속 상태로 존재한다.
   에이전트 연결이 끊겨도 유실되지 않고, 모든 상태는 타임아웃과 종료 조건을 갖는다.
4. **저장소는 자기기술적(self-describing)** — 프레임워크가 유실된 재해 상황에서도
   저장소만으로 무엇을 복구할 수 있는지 알 수 있어야 한다.
5. **자격증명은 최소 범위·최소 수명** — 에이전트에 장기 자격증명을 심지 않고,
   잡 수행에 필요한 범위로 한정된 단기 자격증명을 그때 발급한다. (현재는 "에이전트에 심지 않는다"까지
   구현: 등록된 저장소 키를 잡 claim 때만 전달한다. 범위·수명 한정은 STS 도입 시)
6. **복구는 "제자리 되돌리기"를 전제하지 않는다** — 목표 환경을 파라미터로 받는다.
   마이그레이션 협력(5.2)의 어느 안이 채택되어도 수용할 수 있게 한다.

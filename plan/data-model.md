## 1. 정본(source of truth) 분리

세 곳에 데이터가 있고, **각자 정본인 영역이 다르다.**

| | 프레임워크 DB | 세트별 `manifest.json` | 시스템별 `catalog.db` (구현 파일명 `meta.db`) |
| --- | --- | --- | --- |
| 역할 | 제어 평면 정본 | **복구 정본** | 목록 조회용 색인 |
| 담는 것 | 잡, 실행 시도, 진행 상태, 리스, 전 시스템 이력, 보호 대상 구성 | 확정된 세트의 파일 목록 + 복구 메타데이터 | 세트 목록 요약 |
| 쓰는 주체 | 프레임워크 | 에이전트 (**확정 시 1회, 이후 불변**) | 에이전트 (갱신) |
| 갱신 | 잦음 (진행률 10초 주기) | **없음 (immutable)** | 세트 확정/삭제 시 |
| 손상 시 | 이력·진행 조회 불가 | 해당 세트만 복구 불가 | **매니페스트에서 재생성 가능** |

### 1.1 왜 세트별 불변 매니페스트인가

초기 설계는 시스템별 SQLite 하나에 모든 것을 담았으나, 두 가지 문제가 있다.

- **동시 갱신 충돌** — `systemId`로 이름 충돌을 없애도, 같은 시스템의 백업·삭제·재시도가
  겹치면 `catalog.db`의 download → modify → upload 충돌은 그대로 남는다.
  `pkg/backup/repository/meta_sync.go`의 락은 **호스트 로컬 파일락**이라 다른 VM의
  쓰기를 막지 못한다(2.1절).
- **단일 손상점** — 카탈로그 하나가 깨지면 그 시스템의 **모든** 백업본이 복구
  불가능해진다.

**세트별 `manifest.json`은 확정 시 한 번 쓰고 다시 건드리지 않으므로 동시 갱신 문제가
원천적으로 없다.** `catalog.db`는 매니페스트들로부터 재생성 가능한 색인으로 강등한다.
색인이 깨져도 매니페스트를 훑어 다시 만들면 된다.

원격 객체의 조건부 갱신(S3의 ETag 기반 `If-Match` 등)을 쓰더라도, 그것만으로는
**리스가 만료된 옛 실행 시도의 권한까지 검증되지 않는다.** 확정 권한 통제는 1.3절의
프레임워크 승인으로 처리한다.

### 1.2 왜 프레임워크 DB와 저장소 메타데이터가 둘 다 필요한가

**프레임워크 DB만 두면**: 재해로 프레임워크가 사라졌을 때 저장소에 `.aha` 파일만
덩그러니 남는다. 어느 파일이 어느 시스템의 어느 파일시스템인지, 어떤 코덱인지, 어떤
파일들이 한 세트인지 알 수 없어 복구가 불가능하다. 백업 시스템의 존재 이유에 반한다.

**저장소 메타데이터만 두면**(현행): 전 시스템 교차 조회(SFR-HA-03)를 하려면 조회할
때마다 시스템 수만큼 원격 파일을 내려받아야 한다. 진행률처럼 잦은 갱신은 더 나쁘다 —
`meta_sync.update`는 매 갱신마다 download → modify → upload 왕복이므로, **전체 DB
왕복 비용과 충돌 위험 때문에 진행 보고 경로로 부적절하다.**

### 1.3 확정(commit) 절차

**결과를 만드는 주체(에이전트), 확정을 승인하는 주체(프레임워크), 저장소에 기록하는
주체(에이전트)가 다르다.** 이 사이의 규칙이 없으면 아래 상황에서 상태가 어긋난다.

| 장애 상황 | 규칙이 없을 때의 문제 |
| --- | --- |
| DB에 성공 기록 후 매니페스트 저장 실패 | 성공으로 보이지만 독립 복구에 필요한 정보가 없음 |
| 매니페스트 저장 성공 후 완료 응답 유실 | 저장소엔 확정본이 있는데 프레임워크는 실패로 판단 |
| 리스 만료된 옛 시도가 매니페스트 기록 | 두 시도가 서로 다른 결과를 확정 |
| 확정과 삭제가 동시에 색인 갱신 | 서로의 변경을 덮어씀 |

**확정 절차**:

1. 에이전트가 모든 항목 업로드를 마치고 **확정 요청**을 보낸다.
2. 프레임워크가 **요청한 시도가 현재 유효한 시도인지 검증**하고, 승인 시 산출물
   목록을 **고정**한다. 잡은 `finalizing` 상태가 된다.
3. 에이전트가 고정된 목록으로 `manifest.json`을 기록하고 `catalog.db` 색인을 갱신한다.
4. 에이전트가 확정 완료를 보고한다. **여기까지 끝나야 백업이 성공 처리된다.**

규칙:

- **같은 확정 요청의 재전송은 같은 결과를 반환한다**(고정된 목록을 다시 준다).
- **저장소의 복구 메타데이터까지 영속화된 뒤에 성공 처리한다.** DB만 성공으로 두지
  않는다.
- 확정 중 장애는 `finalizing`으로 남겨 재개한다. 매니페스트가 이미 있으면 그것이
  정답이므로 색인 갱신부터 이어간다.
- 리스가 만료된 시도의 확정 요청은 거부한다.

### 1.4 조정(reconciliation) 경로

"카탈로그를 읽는 경로는 재해 import 외에 금지"는 지나친 제한이다. 장애 후 DB와
저장소의 불일치를 확인할 **제한적 조정 경로**를 둔다.

| 경로 | 성격 |
| --- | --- |
| 정합성 점검 | 관리자가 호출. 시스템 단위로 매니페스트를 훑어 DB와 대조하고 차이를 **보고만** 한다 |
| 색인 재생성 | `catalog.db`를 매니페스트로부터 다시 만든다 |
| 재해 가져오기 | 저장소만 남은 상황에서 프레임워크 DB를 재구성한다 |
| 미확정 산출물 GC | 어느 매니페스트에도 없는 `.aha`와 미완료 multipart를 정리한다 |

전부 **명시적으로 호출하는 도구**이며 상시 양방향 동기화가 아니다. 상시 동기화는
충돌 해소 규칙이 필요해지므로 두지 않는다.

### 1.5 매니페스트에 담을 정보

기준은 "프레임워크 없이 이 저장소만으로 복구할 수 있는가"다.

| 영역 | 항목 |
| --- | --- |
| 형식 | `schemaVersion`, 아카이브 형식 버전 |
| 시스템 | `systemId`, 호스트명, `osInfo`, **`platform`**(3.3절) |
| 세트 | `backupSetId`, `captureStartedAt`, `captureCompletedAt`, `consistencyMode`, `status`, `partial` |
| 항목 | `itemId`, `attemptId`, 대상 식별, **`objectKey`**(저장소 상대 경로), 크기, 체크섬 |
| 검증 | 체크섬 알고리즘과 **계산 대상**(최종 저장 바이트인지 원본 데이터인지) |
| 대상 스냅샷 | 당시 대상 경로, 제외 규칙, 백업 옵션 |
| **레이아웃** | 디스크 → 파티션 → PV/VG/LV → 파일시스템 관계 (4절) |
| 향후 확장 | 암호화 메타데이터(형식·KDF 파라미터, **비밀번호는 제외**), 증분 백업의 부모 관계와 적용 순서 |

단순 파일명 대신 `objectKey`를 쓰는 이유: 저장소 루트가 바뀌거나 백엔드가 달라져도
항목을 찾을 수 있어야 한다.

**매니페스트에 저장소 자격증명을 넣지 않는다.** 매니페스트는 저장소 안에 있으므로,
읽을 수 있는 주체는 이미 자격증명을 가진 것이다.

## 2. 식별자 체계

### 2.1 결함: 시스템 식별자가 hostname이다 — **해소됨 (2026-09-17)**

> `systemId`를 도입해 해소했다(`/var/lib/aiha/system-id`, 등록 후에는 프레임워크가 발급한 값).
> 저장소 경로는 `<systemId>/`이고 hostname은 표시·파일명에만 쓴다. 아래는 당시 기록이다.

`pkg/backup/engine/engine.go`가 `os.Hostname()`을 그대로 시스템 식별자로 쓴다.

```go
hostname, err := os.Hostname()
...
system := model.SystemInfo{ID: hostname, Hostname: hostname}
```

**클라우드에서 이 전제는 깨진다.**

- AWS 기본 hostname은 `ip-10-0-1-5`처럼 **사설 IP 파생**이다. VPC나 계정이 다르면
  전혀 다른 VM이 같은 hostname을 갖는다.
- 오토스케일링·재생성으로 같은 사설 IP가 재할당되면 같은 hostname이 다시 나온다.
- 사용자가 hostname을 바꾸면 같은 VM이 다른 시스템으로 보인다.

저장소 디렉터리와 메타데이터 경로가 hostname 기준이므로, **충돌 시 서로 다른 VM이
같은 메타데이터를 덮어쓴다.**

막아 줄 락도 없다. `pkg/backup/repository/meta_sync.go`의 `lockPath`가 만드는 락은
`/run/lock` 아래의 **호스트 로컬 파일락**이다.

```go
return filepath.Join(m.lockDir, fmt.Sprintf("meta-%s-%s.lock", m.repoID, shortHash(name)))
```

같은 호스트의 프로세스 간에는 동작하지만 **다른 VM 사이에는 아무 보호도 하지 못한다.**
지금은 "시스템 = 호스트"가 1:1이라 우연히 안전할 뿐이다.

**해결**: 프레임워크가 발급하는 안정적 `systemId`를 도입하고, 저장소 경로를 그 기준으로
재정의한다. hostname은 표시용 속성으로 강등한다.

### 2.2 식별자 목록

| 식별자 | 발급 주체 | 수명 | 용도 |
| --- | --- | --- | --- |
| `systemId` | 프레임워크 (등록 시) | 시스템 수명 | 보호 대상 시스템. 저장소 경로 기준 |
| `agentId` | 프레임워크 (등록 시) | 에이전트 설치 수명 | 에이전트 인스턴스 |
| `jobId` | 프레임워크 | 잡 수명 | 논리적 작업 |
| `attemptId` | 프레임워크 (claim 시) | 실행 시도 수명 | 개별 실행 시도 |
| `backupSetId` | 프레임워크 | 백업본 수명 | 한 번의 백업 잡이 만든 묶음 |
| `itemId` | 프레임워크 | 항목 수명 | 세트를 구성하는 개별 산출물 |
| `restoreId` | 프레임워크 | 복구 잡 수명 | 북향에 노출되는 복구 잡 ID |
| `recoveryId` | 프레임워크 | 복구 잡 수명 | 레스큐 환경에 주입되는 ID (남향 전용) |
| `repositoryId` | 프레임워크 | 저장소 등록 수명 | 백업 저장소 |

`systemId`와 `agentId`를 분리하는 이유: 에이전트를 재설치·업그레이드해도 백업 이력이
이어져야 한다. 반대로 복구된 OS에서는 **같은 `agentId`가 다른 시스템에 나타날 수
있다**(2.3절).

### 2.3 복구 시 식별 관계와 자격 격리

세 주체가 등장한다.

| 주체 | 정체 | 자격 |
| --- | --- | --- |
| **원본 시스템** | 백업을 뜬 시스템 | 원래의 `systemId` / `agentId` |
| **레스큐 에이전트** | 복구용 인스턴스의 system-rescue 환경 | 등록된 시스템이 **아님**. `recoveryId` + 1회용 클레임 토큰 |
| **복구 후 에이전트** | 복구된 디스크로 부팅한 OS 안의 에이전트 | **원본 시스템의 자격증명 사본을 그대로 가짐** |

**복구된 OS는 백업 이미지에서 왔으므로 원본의 `systemId`, `agentId`, 에이전트
자격증명을 전부 복제해서 갖는다.** 원본 VM이 아직 살아 있으면 같은 자격을 가진 두
에이전트가 동시에 존재한다.

부팅 확인 토큰([protocol.md](protocol.md) 3.2)만으로는 부족하다. **복구된 OS가 원본
자격증명으로 먼저 롱폴링을 시작하면, 부팅 확인 전에 원본 시스템의 백업 잡을 가져갈 수
있다.** 따라서 순서를 규칙으로 정한다.

1. **레스큐 단계에서 복구 대상 디스크의 원본 에이전트 자격증명을 제거하거나
   비활성화한다.** 에이전트가 이미 그 디스크에 쓰고 있으므로 어렵지 않다.
2. 복구 후 최초 실행은 **일반 작업 수신이 차단된 "복구 등록 모드"** 로 시작한다.
3. 부팅 확인과 새 등록 또는 승계 처리를 수행한다.
4. **유효한 새 자격을 받은 뒤에야 일반 작업 수신을 허용한다.**

**신규 등록과 원본 승계 중 무엇을 택할지는 미결정이어도 되지만
([open-decisions.md](open-decisions.md) 3번), 그동안 일반 작업 수신을 차단한다는
규칙은 지금 확정한다.**

부팅 확인 토큰은 "그 토큰을 가진 주체"임을 증명할 뿐, 그 자체로 예상한 인스턴스나
디스크임을 완전히 증명하지는 않는다. 따라서 토큰을 `recoveryId`·복구 실행 시도·예상
대상 인스턴스와 연결해 저장하고, 만료와 사용 처리 규칙을 함께 둔다.

## 3. 시스템과 플랫폼

### 3.1 도메인 개요

```
Repository ──< System ──< Target
                 │  └── Platform
                 │
                 ├──< Job ──< Attempt ──< ProgressReport
                 │     │
                 │     └── (backup)  ──> BackupSet ──< BackupItem
                 │     │                     └── SourceLayout
                 │     └── (restore) ──> RestorePlan ──> TargetLayoutSpec
                 │
                 └──< Agent
```

### 3.2 System / Agent

| 필드 | 비고 |
| --- | --- |
| `systemId` | 프레임워크 발급. 저장소 경로 기준 |
| `displayName`, `hostname` | 표시용. 변경 가능 |
| `platform` | 원본이 어디서 돌고 있는지 (3.3절) |
| `osInfo` | 배포판, 버전, 커널 |
| `defaultRepositoryId` | **기본** 저장소 설정 |

`defaultRepositoryId`는 기본값일 뿐이다. **실제 저장 위치는 `BackupSet`에 남긴다.**
시스템의 기본 저장소를 바꿔도 과거 백업의 위치는 바뀌지 않기 때문이다.

Agent는 `agentId`, `systemId`, 버전, `lastSeenAt`, 상태, **동작 모드**(일반 /
복구 등록 모드, 2.3절)를 갖는다.

### 3.3 Platform — 원본 실행 환경 정보

백업 시점에 "이 OS가 어디서 돌고 있었는지"를 수집해 백업본과 함께 보관한다.
복구 플랜 수립의 입력이며, 마이그레이션 전략 판단의 근거이기도 하다.

| 필드 | 예시 값 | 용도 |
| --- | --- | --- |
| `cloudProvider` | `aws`, `gcp`, `azure`, `openstack`, `vmware`, `onprem`, `unknown` | 소스/목표 조합 판단 |
| `hypervisor` | `nitro`, `xen`, `kvm`, `hyper-v`, `vmware-esxi`, `bare-metal`, `unknown` | **블록·네트워크 드라이버 결정** |
| `cpuArchitecture` | `x86_64`, `aarch64` | **아키텍처가 다르면 복구 자체가 불가** |
| `virtType` | `hvm`, `pv` | 부팅 방식 |
| `firmware` | `bios`, `uefi` | **부트로더 설치 방식 결정** |
| `secureBoot` | `true` / `false` / `unknown` | 서명된 shim·커널 필요 여부 |
| `diskNaming` | `nvme`, `xvd`, `sd`, `vd` | 디바이스 참조 방식 |
| `nics[]` | 드라이버, MAC, 이름 (**복수**) | 네트워크 재조정 |
| `disks[]` | 크기, 드라이버 (**복수**) | 레이아웃 대조 |
| `accelerators[]` | `nvidia-a100`, TPU/NPU 종류 (**복수**) | AI반도체 호환성 |
| `initramfsModules[]` | 포함된 스토리지·네트워크 모듈 | **부팅 가능성 판정의 핵심** |
| `cloudInitDatasource` | `Ec2`, `GCE`, `Azure`, `NoCloud`, 없음 | 복구 후 재실행 처리 |
| `guestAgents[]` | `ssm-agent`, `vmware-tools`, `qemu-guest-agent` | 목표 환경에 맞게 교체 |
| `instanceType`, `region`, `zone`, `instanceId` | | 인스턴스 생성, 아이덴티티 검증 |
| `collectedAt` | | 수집 시각 |

**모든 필드는 수집 실패를 표현할 수 있어야 한다** (`unknown` 또는 nullable). 온프레미스나
제한된 환경에서 IMDS·DMI 조회가 실패하는 것은 정상이며, 그 때문에 백업이 실패해서는
안 된다.

> **1차년도 구현 범위**: 수집은 한다(비용이 낮고 이력·마이그레이션 판단의 입력으로
> 가치가 있다). 다만 **이 값에 따라 동작을 바꾸는 분기 로직은 구현하지 않는다.**
> 고정 시나리오 하나만 대상으로 하므로 `driverStrategy` 도출도 템플릿으로 고정한다.
> [roadmap.md](roadmap.md) 3절 참조.

#### 왜 필요한가 — 복구에서도 이미 필요하다

마이그레이션만의 문제가 아니다.

- **드라이버 부재로 부팅 불가**: Xen 기반 인스턴스의 백업을 Nitro에 복구하면
  initramfs에 `nvme`·`ena` 모듈이 없어 루트 디스크를 못 찾고 커널 패닉으로 멈춘다.
  복구 절차의 initramfs 리빌드에서 어떤 모듈을 강제 포함할지를 이 정보로 정한다.
- **디바이스 명명 변화**: Xen은 `/dev/xvda1`, Nitro는 `/dev/nvme0n1p1`이다. fstab이나
  grub이 디바이스 경로를 직접 참조하면 부팅에 실패한다(4.5절의 UUID 보존으로 완화).
- **펌웨어 전환**: BIOS → UEFI는 ESP 생성과 `efibootmgr` 등록이 추가로 필요하다.
- **아키텍처 불일치**: `x86_64` 백업을 `aarch64` 인스턴스에 복구하는 것은 불가능하다.
  **플랜 수립 단계에서 거부해야 한다.**
- **cloud-init 데이터소스 불일치**: 다른 프로바이더로 옮기면 엉뚱한 데이터소스를 찾다가
  부팅이 지연되거나 네트워크 설정을 덮어쓴다.
- **게스트 에이전트**: `vmware-tools`가 깔린 OS를 AWS에 복구하면 무의미하게 돌며 실패
  로그만 남긴다.

#### 마이그레이션과의 관계 — 범위 주의

`sourcePlatform`과 `targetPlatform`의 조합이 필요한 작업량을 결정한다.

| 조합 | 필요한 처리 |
| --- | --- |
| 동일 프로바이더 · 동일 하이퍼바이저 | 재조정 최소 |
| 동일 프로바이더 · 다른 하이퍼바이저 (Xen→Nitro) | initramfs 모듈 추가, 디바이스 참조 전환 |
| 다른 프로바이더 | 위 + cloud-init 데이터소스, 게스트 에이전트, 펌웨어 |
| 다른 아키텍처 | **거부** |
| 다른 가속기 | 위 + 드라이버 스택, 경우에 따라 재빌드 |

**범위 주의**: SFR-HA-09(인프라 추천·마이그레이션)와 SFR-HA-11(이종 AI반도체 변환·
최적화)은 연구과제 문서상 한국전자통신연구원 담당이다. 여기서 플랫폼 정보를 수집·
제공하는 것은 **그 판단의 입력을 제공하는 것**이지, 제트컨버터클라우드가 추천·변환
엔진을 구현할 의무를 뜻하지 않는다. 협력 방식은
[open-decisions.md](open-decisions.md) 9번에서 정한다.

#### 수집 방법

에이전트가 `POST /aiha/agent/inventory`로 보고한다. 대부분 OS에서 직접 읽을 수 있다.

- DMI/SMBIOS (`/sys/class/dmi/id/sys_vendor`, `product_name`) — 하이퍼바이저 판별
- `/sys/firmware/efi` 존재 여부 — BIOS/UEFI
- `uname -m` — 아키텍처
- `lsblk`, `/proc/partitions` — 디바이스 명명
- initramfs 내용 (`lsinitrd` 등) — 포함된 모듈
- `/run/cloud-init/` — 데이터소스
- IMDS — 인스턴스 타입/리전 (**실패해도 치명적이지 않게**)
- `lspci`, 가속기 벤더 도구 — `accelerators`

**플랫폼 정보는 백업 세트에 스냅샷으로 함께 저장한다.** 시스템의 현재 값은 백업 이후
바뀔 수 있고(인스턴스 타입 변경, 하이퍼바이저 세대 교체), 복구는 **백업된 OS가
기대하는 환경**을 알아야 하기 때문이다.

## 4. 레이아웃 모델 — 복구 매핑 문제의 해법

### 4.1 문제

프레임워크는 복구용 인스턴스를 **다른 프레임워크를 통해 생성**하고 복구 도구를 주입할
수는 있어도, **그 인스턴스에서 디스크가 어떤 이름으로 보일지 알 수 없다.** 따라서
"이 백업 파일을 `/dev/nvme0n1p2`에 풀어라" 같은 구체적 매핑을 중앙에서 만들 수 없다.

### 4.2 문제 분해

매핑을 **타겟 디바이스 경로**로 표현하려 해서 막히는 것이다. 셋으로 나누면 대부분
사라진다.

| 불확실성 | 해소 방법 |
| --- | --- |
| **크기·기하** | **애초에 없다.** 복구용 인스턴스의 디스크 크기는 프레임워크가 정해서 요청한다 |
| **레이아웃 구조** | **원본에서 안다.** 백업 시점에 수집해 세트에 보관하고 선언적 명세로 내려보낸다 |
| **명명·열거** | **에이전트가 푼다.** 에이전트가 직접 레이아웃을 만들므로 논리↔실제 대응을 안다 |

**따라서 복구 플랜은 `/dev/...` 경로를 담지 않는다. 논리 참조만 담는다.**

### 4.3 SourceLayout — 백업 시점에 수집

**현행 `PartitionSource`는 레이아웃 정보를 전혀 수집하지 않는다.** 디바이스 경로와
마운트 지점만 알 뿐, 파티션 테이블·UUID·크기·LVM 구성이 없다. 전부 신규 작업이다.

| 계층 | 수집 항목 |
| --- | --- |
| 디스크 | 논리 ID, 크기, 파티션 테이블 종류(`gpt`/`mbr`), 역할(`boot`/`data`) |
| 파티션 | 인덱스, 시작·크기, 타입 GUID, 플래그(`boot`, `esp`, `lvm`), 파티션 UUID |
| LVM | PV ↔ VG ↔ LV 관계, **VG/LV 이름**, LV 크기 |
| 파일시스템 | 종류, **`fsUUID`**, 레이블, 마운트 지점, **`totalBytes`**, **`usedBytes`** |
| 기타 | Btrfs 서브볼륨, swap 영역, 원본 `fstab` 원문 + 파싱 결과 |
| 부팅 | 부트 모드, 부트로더 위치, ESP 위치 |

`usedBytes`가 중요한 이유는 4.6절.

### 4.4 TargetLayoutSpec — 프레임워크가 만드는 선언적 명세

원본 레이아웃에서 도출한다. **논리 ID만 사용한다.**

```
logicalDisks:
  - id: disk0    role: boot   requestedSizeBytes: <원본 이상>
  - id: disk1    role: data   requestedSizeBytes: <원본 이상>

diskSelection:
  strategy: bySizeOrder          # 또는 byAttachOrder
  exclude:  rescueMedia, recoveryInfoDisk

layout:
  disk0:
    ptType: gpt
    partitions:
      - id: p1   role: esp     sizeBytes: 512MiB   fsType: vfat   fsUUID: <원본 보존>
      - id: p2   role: root    sizeBytes: rest     fsType: xfs    fsUUID: <원본 보존>
  disk1:
    lvm:
      vg: vg-data                                   # 이름 보존
      lvs: [{ name: lv-data, fsType: ext4, fsUUID: <원본 보존> }]

restoreMap:
  - itemId: item-root   targetRef: { kind: partition, id: p2 }
  - itemId: item-data   targetRef: { kind: lv, vg: vg-data, lv: lv-data }

mountOrder: [ "/", "/boot", "/boot/efi", "/data" ]
```

`targetRef`는 논리 참조다. `/dev/nvme0n1p2`가 아니라 `p2`다.

### 4.5 핵심 기법: 원본 fsUUID를 그대로 재생성한다

파일시스템을 **원본과 같은 UUID로** 만들면, 복구된 `/etc/fstab`과 grub 설정의
`UUID=...` 참조가 **수정 없이 그대로 동작한다.** 재조정 작업의 상당 부분이 사라진다.

| 대상 | 방법 |
| --- | --- |
| ext2/3/4 | `mkfs.ext4 -U <uuid>` |
| XFS | `mkfs.xfs -m uuid=<uuid>` |
| Btrfs | `mkfs.btrfs -U <uuid>` |
| swap | `mkswap -U <uuid>` |
| ESP (vfat) | `mkfs.fat -i <volid>` — 32비트 볼륨 ID이므로 형식이 다름 |
| LVM | LV UUID 대신 **VG/LV 이름을 보존**하면 `/dev/mapper/vg-lv` 경로가 그대로 맞음 |

UUID 보존이 불가능한 대상(ESP의 형식 차이 등)만 fstab 재작성 대상으로 남기면 된다.
즉 **재조정은 "전부 다시 쓴다"가 아니라 "보존 못 한 것만 고친다"** 가 된다.

### 4.6 에이전트의 해석 절차 (레스큐 환경)

1. **실제 블록 디바이스 열거.** 레스큐 미디어 자신과 복구 정보 파일이 든 디스크는
   제외한다.
2. **논리 디스크 ↔ 물리 디스크 대응.** `bySizeOrder`면 크기순으로 정렬해 맞추고,
   각 물리 디스크가 논리 디스크의 최소 크기 이상인지 확인한다.
3. **파괴적 작업 전 실행 가능성 검증** — 이 단계가 필수다.
   - 디스크 개수가 충분한가
   - 각 디스크가 충분히 큰가 (`usedBytes` + 파일시스템 오버헤드 + 여유)
   - 아키텍처·펌웨어가 호환되는가
   - 필요한 도구(`mkfs.xfs`, `lvm`, `grub2-install`)가 레스큐 환경에 있는가
   - **하나라도 어긋나면 포맷하지 않고 중단하고 `plan_mismatch`로 재계획을 요청한다.**
4. 파티션 테이블·파티션·LVM·파일시스템 생성 (원본 UUID·이름 보존).
5. `mountOrder`대로 루트 트리에 마운트.
6. 각 항목을 지정된 마운트 지점에 추출.
7. 재조정 ([Restore.md](Restore.md)).
8. **해석된 실제 매핑(논리 ID → 실제 디바이스)을 프레임워크에 보고**해 이력에 남긴다.

3번은 중요한 원칙이다. **정책과 계획은 중앙에서 정하되, 실제 디스크와 도구의 존재
여부는 에이전트가 확인해야 한다.** 계획과 현실이 다르면 파괴적 작업 전에 멈춘다.

### 4.7 적용 범위 (Tier)

기본 제공 클라우드 이미지는 파티션 구성이 단순한 경우가 대부분이다. 이를 전제로
범위를 나눈다.

| Tier | 구성 | 처리 |
| --- | --- | --- |
| **1** | 단일 부트 디스크 + 선택적 데이터 디스크, 파티션 소수, LVM 없거나 단순 | 자동 |
| 2 | 다중 VG, 복잡한 LVM, Btrfs 서브볼륨 다수 | 명시적 확인 후 진행 |
| 3 | RAID, LUKS, 멀티패스 | **거부**하고 사유 안내 |

Tier를 플랜 수립 시 판정해 사용자에게 미리 알린다. "복구를 시도했다가 중간에
실패"보다 "시작 전에 지원 범위를 알림"이 훨씬 낫다.

> **1차년도 구현 범위**: Tier 판정 로직은 **구현하지 않는다.** 고정 시나리오
> (Ubuntu 24.04 / x86_64 / 단일 디스크 / LVM 없음) 하나만 대상으로 하며, 그 외 구성은
> 지원 대상이 아니다. 판정이 필요해지는 시점에 이 표를 근거로 구현한다.
> [roadmap.md](roadmap.md) 3절 참조.

### 4.8 디스크 크기 정책

프레임워크가 복구 인스턴스의 디스크 크기를 정하므로, **원본 이상으로 요청해 축소
문제를 없앤다.**

- 목표 디스크 == 원본: 그대로 재현
- 목표 디스크 > 원본: 마지막 파티션 또는 지정된 파일시스템을 확장 (`growpart` + `resize2fs`/`xfs_growfs`)
- 목표 디스크 < 원본: **2026 범위에서 지원하지 않는다.** 축소는 `usedBytes` 계산과
  파일시스템별 축소 지원 여부가 얽히므로 별도 기능으로 분리한다.

사용자가 더 작은 디스크를 명시적으로 요청하면 플랜 수립 단계에서 거부한다.

## 5. 백업 대상과 세트

### 5.1 Target — 파티션이 아니라 파일시스템

현행 `pkg/backup/model/model.go`의 `BackupRequest{Device, PartitionName}`는 파티션
전용이다. 그런데 **실제로 백업하는 것은 마운트된 파일시스템의 파일**이지 블록
디바이스가 아니다. LVM LV나 디스크 전체에 직접 만든 파일시스템은 "파티션"에 맞지 않는다.

| `kind` | 대상 | 상태 |
| --- | --- | --- |
| `filesystem` | 마운트된 파일시스템의 파일 백업 | **구현됨** (현행 `partition`을 개칭) |
| `path` | 선택한 디렉터리·파일 백업 | 확장 지점 |
| `blockDevice` | 블록 이미지 백업 | 향후 |
| `container` | 컨테이너 워크로드 (velero, [backup.md](backup.md)) | 인터페이스만 |

**확장 지점 확보와 이번 구현 범위는 구분한다.** SFR-HA-01이 "모델·응용 및 운영
데이터"를 언급한다고 해서 지금 별도의 `path` 백업이나 컨테이너 백업 구현이 필수인
것은 아니다. **해당 데이터가 들어 있는 파일시스템을 백업하는 것으로 충족되는 범위가
있다.** 모델에 자리만 만들어 두고, 구현 범위는 요구가 구체화되면 정한다.

**이중화와의 경계 (2026-11-16, [ha-roadmap.md](ha-roadmap.md) H3b).** 복제 볼륨(DRBD 장치, major 147) 위의
파일시스템은 `filesystem` 대상이 될 수 없다. 인벤토리에 나오되 후보에서 빠지고 사유가 붙는다. 그 데이터는 이중화
그룹이 보호한다(설계서 표 6-4, 운영 데이터 백업은 1차년도 범위 밖). 루트 파일시스템 백업은 복제 리소스 파일
`/etc/drbd.d/*.res`를 담지 않는다 — 공유 비밀이 들어 있다. 매니페스트 `excludedPaths`에 그 패턴이 기록된다.
복제를 구성할 디스크는 인벤토리의 `dataDisks`(파티션·마운트 없는 전체 디스크, `by-id` 경로)로 고른다.

### 5.2 BackupSet — "한 번의 백업 잡이 만든 묶음"

**"이 시점의 VM 전체"라고 표현하면 부정확하다.** `/`를 10:00~10:10에, `/data`를
10:10~10:40에 백업했다면 같은 세트라도 서로 다른 시간대의 데이터다.

여기서 **보호(protection)와 일관성(consistency)을 구분해야 한다.**
`pkg/backup/source/partition_linux.go`의 읽기전용 바인드 마운트는 **보호** 장치이며
그 목적을 제대로 달성한다(5.5절). 다만 **일관성**은 보장하지 않는다.

`mount -B` 후 `remount,ro,bind`는 **그 뷰**를 읽기 전용으로 만들 뿐, 원래 마운트
지점은 계속 쓰기 가능하다. 같은 파일시스템이므로 백업 도중 다른 프로세스가 쓰면 그
변경이 바인드 뷰에도 보인다. 즉 읽기전용 바인드는 **내가 실수로 원본을 건드리는 것**을
막는 장치이지 **남이 원본을 바꾸는 것**을 막는 장치가 아니다. 따라서 **현재 방식은
시점 일관성을 보장하지 않는다.**

따라서 세트는 "한 번의 백업 잡이 만든 묶음"으로 정의하고, 일관성은 **별도 속성으로
정직하게 표현한다.**

| 필드 | 의미 |
| --- | --- |
| `backupSetId`, `systemId`, `jobId`, `repositoryId` | 실제 저장 위치를 여기에 남긴다 |
| `captureStartedAt`, `captureCompletedAt` | **실제 데이터 수집 구간** |
| `consistencyMode` | `live` (실행 중 복사) / `snapshot` / `app-quiesced` |
| `consistencyGroupId` | 일관성 확보 절차를 함께 적용한 대상 묶음 |
| `status`, `partial` | 5.3절 |
| `warnings[]` | 읽는 중 변경된 파일, 누락 등 |
| `osInfo`, `platform`, `sourceLayout` | 백업 시점 스냅샷 |
| `schemaVersion` | |

현재 구현은 `consistencyMode: live`다. 스냅샷 기반 캡처(LVM 스냅샷, 클라우드 볼륨
스냅샷, `fsfreeze`)는 별도 개선 항목으로 둔다 — AI 서비스는 모델 파일 쓰기나 DB가
돌고 있을 수 있어 실무상 중요하다.

### 5.3 완전성: status / partial / committed

세 필드가 서로 모순되는 조합을 표현할 수 있으면 조회·복구 후보 선정 코드마다 판단이
달라진다. 규칙을 정한다.

- **예정 대상 목록을 백업 시작 시 고정한다.** 나중에 무엇이 빠졌는지 알려면 무엇을
  하려 했는지가 기록되어 있어야 한다.
- 각 대상의 **성공 / 실패 / 누락**을 개별 기록한다.
- **세트 확정(`committed`)과 개별 파일 업로드 완료를 구분한다.** 업로드가 끝나도
  프레임워크 승인 전에는 확정이 아니다(1.3절).
- **필수 대상 충족 여부**를 따로 판정한다.
- `partial`은 **계산된 값**이다: 예정 대상 중 성공하지 못한 것이 하나라도 있으면 `true`.

**"5개 중 4개 성공"이라는 숫자보다 어떤 대상이 실패했는지가 중요하다.** 루트
파일시스템 누락과 선택적 데이터 경로 누락은 복구 가능성이 전혀 다르다. 따라서
`requiredTargetsSatisfied`를 별도로 두고, 이것이 `false`인 세트는 **전체 OS 복구
후보에서 제외**한다.

**초기 구현 단순화**: 한 세트의 확정 산출물은 **하나의 Attempt에서만** 선택한다.
실패한 항목만 재시도해 여러 시도의 결과를 섞으려면 선택 규칙과 시간 일관성 정의가
추가로 필요하므로, 지금은 세트 전체를 다시 수행한다.

### 5.4 BackupItem

| 필드 | 비고 |
| --- | --- |
| `itemId`, `backupSetId`, `attemptId` | |
| `targetId`, `targetKind` | 무엇을 백업했는지 |
| `objectKey` | 저장소 상대 경로 |
| `sizeBytes`, `checksum`, `checksumAlgo`, `checksumScope` | **무엇을 대상으로 계산했는지** 명시 |
| `compression`, `scheme` | |
| `status`, `message` | |
| `committed` | 정본으로 확정되었는지 |

`checksumScope`는 `stored-bytes`(최종 저장된 압축 바이트) 또는 `source-data`(압축 전
원본 데이터) 중 하나다. 둘은 용도가 다르다 — 전자는 전송 무결성, 후자는 복구 후
검증에 쓴다.

### 5.5 읽기전용 바인드 마운트가 실제로 보장하는 것

5.2절이 "시점 일관성을 보장하지 않는다"고 해서 바인드 마운트가 불필요하다는 뜻은
아니다. **이 설계에 필수적이며, 네 가지를 보장한다.**

| 보장 | 내용 |
| --- | --- |
| **atime 갱신 차단** | 대부분 배포판 기본값 `relatime`은 atime이 mtime/ctime보다 오래됐거나 24시간을 초과하면 atime을 갱신한다. **전체 트리를 읽기만 해도 원본에 대량의 메타데이터 쓰기가 발생한다.** 커널 `touch_atime()`은 마운트가 읽기전용이면 갱신을 건너뛰므로, ro 뷰로 읽으면 **원본에 대한 쓰기가 0건**이다. 원본을 `noatime`으로 remount하는 침습적 방법을 피하면서 같은 효과를 얻는다 |
| **커널 강제 쓰기 차단** | 아카이버는 root로 트리를 순회한다. root의 실수를 막는 유일한 장치가 ro 마운트다. 코드 버그나 향후 기능이 그 경로로 쓰기를 시도하면 EROFS로 거부된다 |
| **하위 마운트 배제** | `MS_BIND`만 쓰고 `MS_REC`를 쓰지 않는 **비재귀 바인드**라 하위 마운트가 딸려오지 않는다. `/`를 바인드하면 `/proc`·`/sys`·`/dev`·`/run`은 물론 **별도 파티션인 `/boot`, 데이터 디스크, 네트워크 마운트까지 빈 디렉터리로 보인다.** 이것이 "파티션 단위 백업"이라는 설계를 성립시킨다 |
| **고정 작업 경로** | 파티션이 어디에 마운트돼 있든 아카이버는 일정한 임시 경로에서 작업한다 |

**세 번째가 실질적으로 가장 크다.** 없으면 `/` 백업이 `/proc/kcore`(RAM 크기의 가상
파일) 같은 것으로 기어들어가거나 다른 파티션을 통째로 빨아들인다.

`pkg/backup/source/exclude.go`의 `^dev/`, `^proc/` 패턴은 이와 중복이 아니다.
**바인드는 *마운트된* 의사 파일시스템을 배제하고, exclude는 그 마운트 지점의 *디스크상
잔여 내용*을 제거한다.** 디렉터리 항목 자체는 남겨 복구된 시스템이 마운트할 자리를
유지하는 것도 의도된 동작이다.

따라서 일관성 개선([open-decisions.md](open-decisions.md) 11번)을 도입하더라도
**바인드 마운트를 걷어내는 것이 아니라, 스냅샷 대상 위에 같은 방식으로 바인드를 얹는
형태가 된다.**

### 6.2 결함: 진행률 보고 경로가 없다 — **부분 해소**

> 백업 잡은 `/progress`로 업로드 바이트(`countingWriter`)와 단계를 프레임워크에 보고하고(2026-09-17),
> 복구 잡은 단계 n/6과 저장소에서 읽은 바이트를 보고한다(2026-10-08). 원본 기준 진행률
> (`sourceProcessedBytes`, 6.3)은 아직 없다. 아래는 당시 기록이다.

현행 엔진은 시작과 종료만 기록한다. **`pkg/backup/engine/engine.go`의
`countingWriter`는 저장소 writer를 감싸므로 압축 후 전송 바이트를 센다.** 원본 처리량은
세지 않는다. 원본 기준 진행률을 얻으려면 `pkg/backup/archive`의 tar 워크 루프에
별도 훅이 필요하다.

주의할 점 둘:

1. **진행 보고는 저장소가 아니라 프레임워크로 간다.** `meta_sync.update`의 download →
   modify → upload 왕복은 전체 DB 왕복 비용과 충돌 위험 때문에 이 경로로 부적절하다.
2. **보고 루프와 처리 루프를 분리한다.** 백업 처리가 멈춰도 생존 보고는 계속되어야
   한다([protocol.md](protocol.md) 2.4).

### 6.3 진행률 지표

`processedBytes / totalBytes` 하나로는 기준이 불분명하다. **세 가지를 구분한다.**

| 지표 | 기준 | 출처 |
| --- | --- | --- |
| `sourceProcessedBytes` / `sourceTotalBytes` | 원본 파일 처리량 | tar 워크 루프에 신규 훅. 총량은 `usedBytes`로 사전 파악 가능 |
| `archiveProducedBytes` | 생성한 압축 아카이브 양 | 압축기 출력 |
| `uploadedBytes` | 업로드가 확인된 양 | 현행 `countingWriter`, `spool` 청크 |

**압축 후 총량이 미확정이라는 이유로 원본 처리 진행률까지 미확정으로 둘 필요는 없다.**
`sourceTotalBytes`는 백업 시작 전 `usedBytes`로 알 수 있으므로, 사용자에게 보여줄
백분율은 원본 기준으로 계산한다.

## 7. RestorePlan

**현행 (2026-10-12)**: 플랜은 `{sourceSystemId, sourceBackupSetId}` 두 값뿐이고 프레임워크가 세트 ID로
만든다. 항목 목록은 넣지 않는다 — 레스큐가 저장소의 매니페스트에서 읽는다. 저장소 접근은 플랜이 아니라
복구 잡의 `repository_id`로 등록된 저장소를 가리키고, claim 응답을 만들 때 복호화해 싣는다
(단기 자격증명이 아니라 등록된 키). `targetLayoutSpec`·`driverStrategy`·`tier`·`bootVerifyToken`은
1차년도 범위 밖이다. 아래는 목표 모델이다.

| 필드 | 비고 |
| --- | --- |
| `restoreId`, `recoveryId` | 분리 ([protocol.md](protocol.md) 4.2) |
| `sourceBackupSetId` | 복구 원본 |
| `items` | 복구할 항목 목록 (`objectKey` 포함) |
| **`targetLayoutSpec`** | 4.4절. **논리 참조만 포함** |
| `sourcePlatform` / `targetPlatform` | 3.3절 |
| `driverStrategy` | 두 플랫폼 차이에서 도출한 조치 — initramfs 강제 포함 모듈, 부트로더 설치 방식 |
| `reconciliation` | 재조정 항목 지시 ([Restore.md](Restore.md)) |
| `repositoryAccess` | **단기 스코프 자격증명** |
| `bootVerifyToken` | 복구된 디스크에 심을 1회용 부팅 확인 토큰 |
| `frameworkEndpoint` | 에이전트가 보고할 주소 |
| `tier` | 4.7절 판정 결과 |

`repositoryAccess`는 **프레임워크 DB에 장기 보관하지 않는다.** 복구 잡 수명 동안만
유지하고 종료 시 폐기한다.

`targetPlatform`을 원본과 분리하는 이유: 복구는 "원래 있던 자리로 되돌린다"를
전제하지 않는다. 목표 클라우드가 다르면 그것이 곧 마이그레이션이다
([architecture.md](architecture.md) 5.2).

## 8. 저장소 레이아웃

**현행 (2026-09-17 구현):**

```
<repository-root>/
  <systemId>/
    meta.db                                 재생성 가능한 색인
    <backupSetId>-manifest.json             복구 정본 (불변)
    <hostname>-<partition>-<randomId>.aha   randomId는 세트·항목 ID와 별개
```

**세트 계층을 두지 않고 평면으로 갔다.** 모든 저장소 백엔드(local/sftp/smb/s3)가
파일명에 경로 구분자가 있으면 거부하는데, 이는 파일명이 시스템 디렉터리 밖으로
나가는 것을 막는 방어다. 중첩 디렉터리를 쓰려면 그 검증과 경로 조립을 백엔드 5곳에서
고쳐야 하고, 얻는 것(세트 단위 prefix 삭제)에 비해 건드리는 곳이 경로 보안이라 값이
비쌌다. 세트 id를 파일명에 담고, **그룹핑은 매니페스트가 아이템 파일명을 나열해**
유지한다.

매니페스트를 `meta.db`와 나눈 이유는 네 가지다. 첫 번째가 결정적이다.

1. **레스큐 바이너리에 SQLite를 링크하지 않기 위해서다.** 복구 메타데이터가 `meta.db`
   안에만 있으면 `aiha-rescue`가 `modernc.org/sqlite`를 링크해야 해서, 경량 빌드를
   만든 이유와 어긋난다. JSON이면 `rclone cat` + `encoding/json`으로 끝난다.
2. `meta.db`는 갱신할 때마다 파일 전체를 내려받고 다시 올린다. 세트마다 불변인 수십
   KB의 시스템 정보를 넣으면 **이후 모든 백업의 왕복 비용**이 늘어난다.
3. `meta_sync`의 잠금은 호스트 로컬 파일 락이라 **다른 VM 사이에서는 보호가 없다**
   (2.1절). 경로가 유일하고 1회만 쓰는 매니페스트는 그 경합 자체가 없다.
4. `meta.db`를 잃어도 저장소만으로 복구할 수 있어야 한다. 색인은 다시 만들면 된다.

반대로 매니페스트만 두고 `meta.db`를 없애지 않는 이유는 목록 조회다. 세트가 N개면
매니페스트 N개를 네트워크로 읽어야 한다.

**나중에 세트 계층으로 옮긴다면** 백엔드의 경로 검증을 세트 한 단계만 허용하도록
고치는 것이 선결 과제다.

파일명에 `attemptId`를 넣으면 시도별 분리가 이름만으로 드러난다. 현행
`model.BackupFileName`이 이미 호출마다 랜덤 ID를 붙이므로 분리 자체는 성립하고 있고,
그 랜덤 ID를 `attemptId`로 대체하면 **저장소의 파일과 프레임워크의 실행 시도가 직접
대응**되어 미확정 산출물 추적이 쉬워진다.

`.aha` 확장자와 압축 방식은 [backup.md](backup.md)를 따른다.

## 9. 프레임워크 DB

DB는 **PostgreSQL로 확정**되었다 — [open-decisions.md](open-decisions.md) 6번 (해소됨). **다만 DB 제품
선택보다 1.3절(확정 절차), 2.3절(복구 에이전트 자격 격리), 5.3절(세트 완전성),
1.5절(복구 메타데이터 명세)이 복구 신뢰성에 훨씬 직접적인 영향을 준다.** 그쪽을 먼저
확정한다.

선택에 영향을 주는 요구사항:

- **동시 쓰기** — 진행 보고가 에이전트당 10초 주기로 들어온다. 실행 중인 잡이 100개면
  진행 보고만 **평균 초당 10건**이고, 리스 갱신·상태 전이·이벤트를 더하면 늘어난다.
  대부분 같은 행의 갱신이다.
- **원자적 claim** — 조건부 갱신(`UPDATE ... WHERE status='queued'`)의 원자성이
  보장되어야 한다([protocol.md](protocol.md) 2.3).
- **교차 조회** — SFR-HA-03의 전 시스템 이력 조회. 기간·상태·시스템 필터와 정렬.
- **정리** — 만료된 잡, 오래된 진행 보고의 주기적 삭제.

진행 보고를 메모리에서 병합하고 주기적으로 영속화하는 방식도 가능하지만, 그 경우
프레임워크 재시작 시 리스 상태를 잃지 않도록 **리스만은 즉시 영속화**해야 한다.

신규 의존성을 도입한다면 CLAUDE.md의 [Third-Party Package Policy]에 따라 표준
라이브러리 우선 검토, 라이선스 확인(Apache 2.0 호환), 유지보수 지표 보고 후 승인이
필요하다.

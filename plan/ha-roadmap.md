# 이중화 구현 로드맵 (1차년도 프로토타입)

TM-AI-HA-02 V1.0 「AI 서비스 이중화 구성 및 데이터 복제·전환 구조 설계서」

에이전트에 구현하는 순서와 범위를 정한다. 대상 요구사항은 **SFR-HA-04, SFR-HA-05**, 시나리오는
**HA-01, HA-02, HA-03, HA-08**이다.

## 1. 목표

설계서 그림 6-1의 연말 검증 항목 4개를 프레임워크를 통해 시연한다.

| 검증 항목 | 완료 모습 | 단계 |
| --- | --- | --- |
| 복제 대상 등록 | `ha create`로 두 시스템, 데이터 볼륨, 서비스 정의 등록 | H1, H3 |
| 초기 동기화 | `ha setup` 후 운영 → 대기 전체 복사, 소요 시간 측정 | H3 |
| 복제 상태 관리 | `ha status`로 연결·동기화·오류 조회, 상태 변화 이력 | H1 |
| 수동 전환 | 계획 전환, 운영 인스턴스 정지 후 장애 전환 | H4 |

고정 시나리오는 설계서 표 6-2를 따르되 클라우드를 넓힌다. 1차년도 대상 클라우드는 **AWS, GCP,
Azure**이고 이후 다른 퍼블릭 클라우드가 추가된다. 한 클라우드 안에서 한 리전의 두 가용 영역, 같은
가상 네트워크, Ubuntu 24.04 x86_64, 같은 사양 인스턴스 2대, 루트 + 데이터 볼륨 1개, DRBD 리소스
1개(Protocol C, 단일 Primary), 서비스 유닛 1개와 HTTP 헬스 경로, 승인 기반 수동 전환, 서비스 주소는
운영자가 수동 재지정. 클라우드 사이의 구성은 후속 단계다(설계서 3.4). 일반화하지 않는다는 방침은
[roadmap.md](roadmap.md) 3절과 같다.

새 Go 의존성은 필요 없다. DRBD, systemd, `nvidia-smi`는 외부 프로세스로 실행하며(설계서 표 4-1),
HTTP·TCP 점검은 표준 라이브러리로 충분하다.

### 1.1 클라우드 중립

클라우드가 늘어도 코드는 바뀌지 않게 한다.

- 프레임워크와 에이전트는 **클라우드 API를 호출하지 않고 클라우드별로 분기하지 않는다.** 노드에서
  보는 것은 Linux 표준 인터페이스(udev, systemd, DRBD, `lsblk`)뿐이다.
- 데이터 볼륨은 udev의 `/dev/disk/by-id/<ID-LINK>`로 가리킨다. 이름 형태는 클라우드마다 다르지만
  (AWS `nvme-Amazon_Elastic_Block_Store_vol…`, GCP `google-<장치 이름>`, Azure `scsi-3<WWN>`) 코드는
  형태를 해석하지 않고, 인벤토리가 보고한 값을 그대로 쓴다. 커널 장치 이름(`sdb`, `nvme1n1`)은 어느
  클라우드에서도 부팅마다 바뀔 수 있다고 보고 신원으로 쓰지 않는다(Azure에서 재부팅으로 바뀐 것을 확인,
  [ha-h0.md](ha-h0.md) 13.1절).
- 클라우드가 개입해야 하는 일 — 인스턴스 정지(펜싱), 서비스 주소 재지정, 방화벽 — 은 운영자가 하고
  프레임워크는 기록만 받는다. 자동화는 `InfraProvisioner`가 생긴 뒤다(9절).
- 클라우드마다 달라질 수 있는 것(커널 flavor와 DKMS 빌드, `by-id` 이름)은 코드가 아니라
  설치 전제로 다루고, [ha-h0.md](ha-h0.md) 13절의 보완 확인으로 검증한다.
- **Secure Boot는 항상 비활성을 기준으로 한다.** 백업·복구와 이중화 공통의 이용 제한사항으로 명시하고(7절 결정 5,
  [roadmap.md](roadmap.md) 3.1절), 검증이나 코드의 분기 대상으로 삼지 않는다. 세 클라우드 모두 끌 수 있음을
  확인했다([ha-h0.md](ha-h0.md) 0절, 13.1절).
- `drbd-utils`를 설치하면 `drbd.service`는 **기본이 disabled**다. 그대로 둔다(7절 결정 7).

## 2. 단계 순서

```text
H0 수동 검증 ──> H1 헬스체크 ──> H3a 잡 큐 일반화 ──> H3b 복제 구성 ──> H4 전환 ──┐
                                                                                 ├─> 시드 포함 전체 흐름
H2 대기 시스템 등록 ─────────────────────────────────────────────────────────────┘
```

| 단계 | 내용 | 선행 | 실행 주체 |
| --- | --- | --- | --- |
| H0 | DRBD 수동 검증, 구현 결정에 필요한 실측 — **AWS 완료(2026-11-12)** | 없음 | 운영자(클라우드 VM), [ha-h0.md](ha-h0.md) |
| H1 | 그룹 등록, 헬스 보고, 판정, 조회 | H0 | 구현 |
| H3a | 잡 큐에 백업 외 종류를 싣는 공통 변경 — **구현(2026-11-13)** | 없음 | 구현 |
| H3b | 작업 흐름, 복제 구성·해제, 공유 비밀, 초기 동기화 — **구현(2026-11-16)**, 실환경 검증 남음 | H0, H1, H3a | 구현 |
| H4 | 강등·승격, 승인·펜싱, 재합류, 전환 이력 | H1, H3b | 구현 |
| H2 | 복구된 시스템의 신규 등록, 계보, 대기 시드 | 없음 | 구현, H4 뒤 |

설계서 표 6-3과 다른 점이 둘 있다.

1. **HA 그룹 등록을 H3에서 H1로 당긴다.** 에이전트가 무엇을 점검할지(서비스 유닛, 포트, 헬스
   경로, 상대 주소)는 그룹 정의에서 오므로, 그룹 없이는 H1이 동작하지 않는다. H1의 그룹은
   메타데이터만 등록하고 복제는 건드리지 않는다. 덕분에 H1은 H0에서 손으로 만든 DRBD 리소스를
   대상으로 실환경에서 바로 검증할 수 있다.
2. **H2를 H3의 선행에서 빼고 H4 뒤에 한다 (7절 결정 1).** 연말 검증 4개 중 시드를 요구하는 항목이
   없고, 같은 AMI로 만들어 일반 등록한 인스턴스도 대기 노드 역할을 할 수 있다. H3·H4는 이 수동
   구성 대기로 검증하고, H2가 끝나면 시드부터 이어지는 전체 흐름을 한 번 더 확인한다.

## 3. 코드 출발점

기준 시점 2026-11-02. `go build`, `go vet`, `go test ./...` 통과 (PostgreSQL 통합 테스트 제외).

### 3.1 그대로 재사용하는 것

| 구성 요소 | 위치 | 이중화에서의 쓰임 |
| --- | --- | --- |
| 잡 큐, 리스, 스위퍼, 보고 루프 | `pkg/framework/job`, `pkg/agent/worker` | 구성·전환 잡 전달. 리스 만료 시 재실행하지 않는 규칙, 시작 보고가 승인되기 전에는 아무것도 하지 않는 규칙 유지 |
| 외부 명령 실행부 | `sysinfo.Runner` / `ExecRunner` | DRBD·systemd·`nvidia-smi` 실행. 복구 실행기와 같은 방식으로 재사용하고 새로 만들지 않는다 |
| 자격증명 암호화 | `pkg/framework/secret` (`Seal`/`Open`, AAD) | 복제 공유 비밀 보관 |
| 주기 보고 패턴 | `aiha-agent/cmd/inventory.go` `reportInventory` | 헬스 보고 루프의 형태 |
| 서버 주기 작업 | `aiha-framework/cmd/server.go` `runSweeper` | 헬스 평가·작업 흐름 진행 루프의 형태 |
| 멱등 스키마 적용 | 패키지별 `schema.sql` + `Migrate` | `ha` 스키마 |
| 요청 키 기반 멱등성 | 등록의 `registrationKey`, 복구 claim의 재수신 | boot-verify 재요청 |

### 3.2 고쳐야 하는 것

설계서 표 6-1은 잡 큐 변경을 "작업 종류 추가"로 적었지만, 실제로는 큐가 백업을 전제하는 지점이
여러 곳이다.

| 위치 | 현재 | 변경 | 단계 |
| --- | --- | --- | --- |
| `job/schema.sql` | `kind`가 `'backup'`만 허용 | 종류 추가. `Migrate`는 CLI 실행마다 돌므로 조건부 멱등 SQL로 작성 | H3a(완료) |
| `job.Service.Claim` → `repositoryFor` | 모든 잡에 저장소를 요구. 비백업 잡은 `ErrLegacyJob` | 종류별 분기 | H3a(완료) |
| `job.Service` | TTL이 서비스 전체에 하나(기본 24h) | 종류별 TTL | H3a(완료) |
| `job.Store.Insert` | 자기 커넥션으로 삽입 | 호출자의 트랜잭션 안에서 삽입하는 경로 (작업 흐름 단계와 같은 트랜잭션) | H3a(완료) |
| `job.Service.CreateBackup`, `Claim`, `RecordProgress` | 이중화를 모름 | 주입된 인터페이스로 확인: 진행 중 작업 흐름이 있는 시스템의 백업 잡 생성 거절, HA 잡은 claim과 시작 보고 때 흐름 유효성 확인. `job`이 `ha`를 import하지 않게 한다 | H3a(완료) |
| `model.AgentJobClaimResp` | 잡 종류와 복제 비밀을 담을 자리 없음 | `kind`, `replication` 추가 (기존 필드는 유지) | H3a(완료) |
| `worker.Runner`, `backupRunner` | 백업 전제 시그니처 | 종류를 받아 실행기로 분배 | H3a(완료) |
| `sysinfo.judge` | DRBD 위 파일시스템이 백업 후보가 됨 | 후보 제외 + 사유 표시 (설계서 표 6-1) | H3b(완료) |
| `sysinfo.Partitions` | 마운트된 것만 보여 빈 데이터 볼륨을 알 수 없음 | 인벤토리에 미마운트 디스크 추가 | H3b(완료, `sysinfo.DataDisks`) |
| `source.PartitionSource.Excludes` | `/var/lib/aiha`만 제외 | 복제 리소스 파일 제외 (4절 항목 6) | H3b(완료) |
| `cmd/run.go`, `restore.go`, `state` | 복구 표식이 있으면 종료 코드 11로 멈춤. 부팅 확인 없음 | boot-verify 구현 | H2 |
| `sh/aiha-init.sh` | 표식 파일로 user-data 재실행을 막음 | 표식을 지우지 않는 방식에 맞춤 (4절 항목 13) | H2 |

## 4. 설계서에 보강하는 사항

코드와 대조해 드러난 것과 외부 검토(10절)에서 나온 것이다. 대부분 설계서의 의도를 구현 수준으로
채우는 내용이며, 설계서와 달라지는 항목은 **(변경)** 으로 표시했다.

| # | 항목 | 왜 필요한가 | 처리 | 단계 |
| --- | --- | --- | --- | --- |
| 1 | 재합류 | 설계서 4.6은 복귀한 옛 운영 노드의 변경분을 버리고 재동기화한다고 하나 표 4-6에 작업이 없다. H0 확인: 옛 운영 노드가 연결된 채 멈췄으면 DRBD가 스스로 재동기화하고, 단절 뒤에 썼으면 양쪽이 분할 뇌로 `StandAlone`에 멈춘다(ha-h0 12절 11번) | 잡 종류 `ha-rejoin` 추가. 분할 뇌일 때만 `--discard-my-data`. 되돌릴 수 없으므로 운영자의 명시 요청으로만 실행하며, 펜싱 해제를 겸한다 | H4 |
| 2 | 자동 승격 차단 | 재부팅한 노드가 Secondary로 올라온다는 전제는 설정으로 보장해야 한다. DRBD 9는 마운트나 쓰기용 열기에 따른 자동 승격이 기본으로 켜져 있다 | DRBD 9는 `auto-promote no`, 8.4는 `become-primary-on` 미설정. 재부팅 뒤 복귀는 역할 변경 없는 `ha-promote`(`ha resume`). H0 확인: `auto-promote no`에서 운영 노드 재부팅 뒤 Secondary, 마운트·서비스 없음(ha-h0 12절 8번) | H0, H3b, H4 |
| 3 | 첫 승격과 포맷 | `replication-setup`은 리소스 기동까지여서 첫 승격(`--force`)과 `mkfs`의 주체가 없다 | 잡 명세의 `initialPrimary`로 구분. 첫 승격은 양쪽 디스크가 모두 `Inconsistent`일 때만 | H3b |
| 4 | 장치 오지정·재포맷 방지 | `create-md`, `mkfs`는 파괴적이고, 자동 재시도가 없어도 운영자의 재요청은 생긴다 | 실행 전 검사(미마운트, 루트 디스크 아님, 양쪽 크기 일치)와 단계별 상태 확인 후 실행: 메타데이터가 있으면 `create-md` 생략, 파일시스템이 있으면 `mkfs` 생략, `create-md --force`는 쓰지 않는다. H0 확인: 메타데이터는 `drbdadm show-gi` 성공(없으면 실패)과 하위 디스크 `blkid`의 `TYPE="drbd"`로 판별된다. 그 밖의 서명이 있으면 거절한다. `create-md`는 TTY가 없으면 덮어쓰지 않고 취소한다(ha-h0 12절 13·14번) | H3b |
| 5 | 장치 경로 | 설계서 예시의 `/dev/nvme1n1`은 인스턴스마다 바뀐다 (복구에서 원본 `nvme1n1`, 타깃 `nvme0n1`을 실제로 겪음). 같은 인스턴스에서도 부팅마다 바뀔 수 있다(Azure 재부팅에서 `sda`·`sdb`가 바뀜, ha-h0 13.1절). 클라우드마다 장치 종류(NVMe, SCSI)와 이름 형태도 다르다 | udev `/dev/disk/by-id/<ID-LINK>` 경로 사용(1.1절). 인벤토리가 `lsblk`의 `ID-LINK`로 디스크마다 보고하고, 코드는 형태를 해석하지 않는다 | H3b |
| 6 | 공유 비밀 유출 경로 | ① 잡 `spec`은 DB에 평문 저장되고 롱폴 응답으로도 나간다. ② `/etc/drbd.d`는 루트 백업과 시드에 그대로 들어간다 | ① 비밀은 claim 응답으로만 전달. ② 리소스 파일을 백업에서 제외하고 매니페스트 `excludedPaths`에 기록 | H3a, H3b |
| 7 | 리소스 파일 생성 위치 **(변경)** | 설계서 4.4는 프레임워크가 파일을 생성한다고 하나, 그러면 비밀이 든 원문이 잡을 통과한다 | 프레임워크는 구조화된 명세를 보내고 에이전트가 비밀과 합쳐 `0600`으로 작성 | H3b |

### H1 — 헬스체크 보고

**구현 (브랜치 `ha/h1-health`)** — 2026-11-09에 복제 상태 수집을 뺀 전부를, 2026-11-12에

이 절 끝의 "구현 메모".

#### 프레임워크

- `pkg/framework/ha` 신설: `schema.sql`, `Store`/`PGStore`, `Service`, `evaluate.go`.
- 스키마 3종. `ha_groups`(복제 리소스, 서비스 정의, 상태, 그룹별 이벤트 순번), `ha_nodes`(시스템당
  PK로 한 그룹만 소속, 역할, 주소, 펜싱 여부, 최근 보고), `ha_events`(그룹별 순번의 상태 변화 이력,
  4절 항목 17).
- 판정은 `Evaluate(now, 운영 보고, 대기 보고, 임계값)` **순수 함수**로 둔다. 설계서 표 5-1, 5-3을
  표 기반 테스트로 옮긴다.
- 그룹 상태 변경은 기대하는 현재 상태를 조건으로 건 UPDATE로만 한다. 평가기는 6절 표에서 허용된
  전이만 한다.
- `POST /aiha/agent/health`: 최근 보고 저장, 판정, 상태가 바뀌면 이벤트 기록. **응답으로 배정 정보를
  돌려준다** — 역할, 서비스 정의, 상대 주소, 보고 주기. 서비스 정의를 전달하는 경로가 따로 필요
  없고, 프레임워크가 노드에 접속하지 않는다는 원칙에 맞는다. 그룹에 속하지 않은 에이전트는
  미배정 응답을 받는다.
- 마지막 동기화 확인 시각(양쪽이 `Connected`·`UpToDate`로 보고한 마지막 시각)을 그룹에 기록한다.
  H4의 장애 전환 화면과 이력이 이 값을 쓴다.
- 서버 주기 루프 `runHAEvaluator`: 보고가 끊긴 경우는 보고가 오지 않으므로 틱으로 판정한다.
- CLI: `aiha-framework ha create | list | status | events`. `ha create`는 H0 리소스를 가리킬 수
  있도록 `--resource`를 받는다.
- 설정: `AIHA_FRAMEWORK_HA_REPORT_INTERVAL`(30s), `AIHA_FRAMEWORK_HA_STALE_AFTER`(90s).
  `conf/template-setup.env`에 기록.

#### 에이전트

- `pkg/agent/ha/drbd`: 역할, 연결, 디스크, 미동기량 조회. `sysinfo.Runner`를 받는다. DRBD 9의
  `drbdsetup status --json <리소스>`만 읽는다(7절 결정 6). 픽스처는 H0 2차 시도의 원문 10개다.
- `pkg/agent/ha/health`: 서비스 유닛, 로컬 포트, 헬스 API(상태 코드·지연), 상호 프로브, GPU, 복제.
  노드 역할에 따라 기대값이 다르며, 그 판단은 프레임워크가 한다. 에이전트는 측정값만 보낸다.

### 작업 흐름 공통 규칙 (H3b, H4)

구성(`setup`), 해제(`teardown`), 전환(`switchover`, `failover`, `resume`, `rejoin`)은 모두 같은
작업 흐름 장치 위에서 돈다. 프레임워크가 재시작해도 안전하려면 DB 상태 기반 루프만으로는 부족하므로
다음을 지킨다.

- **그룹당 진행 중인 흐름은 하나.** 부분 유니크 인덱스로 보장한다.
- **단계 전진과 그 단계의 잡 생성은 한 트랜잭션이다.** `(흐름 ID, 단계, 대상 시스템)`에 유니크
  제약을 두어, 잡을 만든 직후 프레임워크가 죽어도 재시작 뒤 같은 잡을 다시 만들지 않는다.
- **다음 단계는 앞 단계를 확인한 뒤에만 발행한다.** 서로 다른 에이전트 사이에서는 발행 순서가 실행
  순서를 보장하지 않는다. 앞 단계 잡이 `completed`이고, 그 결과가 해당 노드의 헬스 보고와 맞을 때만
  다음 잡을 만든다(예: 대기 구성 완료 → 대기 보고에 리소스가 Secondary로 올라와 있음).
- **늦게 도착한 잡은 실행되지 않는다.** HA 잡 명세에 흐름 ID와 단계가 들어가고, 프레임워크는 claim과
  시작 보고 때 흐름이 아직 그 단계에 있는지 확인한다. 에이전트는 시작 보고가 승인되기 전에는 아무것도
  하지 않으므로(기존 규칙), 흐름이 끝났거나 바뀐 뒤의 잡은 손대기 전에 거절된다.
- **실패나 결과 미확인이면 멈춘다.** 흐름과 그룹은 `error`가 되고 다음 잡을 내지 않는다. 자동 재시도는
  없다. 결과가 유실된 잡은 실제 노드 상태를 확인하기 전까지 다음 단계로 가지 않는다.
- **`ha acknowledge`는 확인 뒤에만 `error`를 푼다.** 그룹의 시스템에 대기·실행 중인 HA 잡이 없고,
  연락되는 노드의 최신 보고가 기록된 역할과 맞을 때만 해제한다. 맞지 않으면 무엇이 다른지 보여 주고
  거절한다.

### H3b — 복제 구성

**구현 (2026-11-16, 브랜치 `ha/h1-health`)** — H1·H3a와 같은 브랜치다. H1·H3a가 아직 커밋 전이고 H3b가 그
파일들(`aiha-framework/cmd/setup.go`·`server.go`·`ha.go`, `aiha-agent/cmd/run.go`, `pkg/framework/job`)을 다시
고치기 때문이다(H3a와 같은 8절 예외). 계약은 [protocol.md](protocol.md) 3.5절, 구현하며 정한 것은 이 절 끝의
"구현 메모". 남은 것은 실환경 검증이다.

- `ha setup <group>`: 공유 비밀을 생성·암호화하고 구성 흐름을 시작한다. 1단계는 대기 노드의
  `replication-setup`, 대기 완료가 확인되면 2단계로 운영 노드의 `replication-setup`(`initialPrimary`).
- 잡 명세 `ReplicationSetupSpec`: 흐름 ID·단계, 리소스, 장치, 메타데이터, 프로토콜, 양쪽 호스트명·주소,
  마운트 지점, 서비스 유닛, `initialPrimary`. 비밀은 포함하지 않는다.
- 에이전트 실행기는 단계마다 **현재 상태를 확인하고 필요한 것만 한다** (4절 항목 4).
  1. 실행 전 검사: 장치, 크기, 서비스가 정지되어 있는지. 서비스가 돌고 있으면 거절한다 — 구성 도중
     서비스가 기존 `/data`에 쓰는 것을 막는다.
  2. 리소스 파일 작성(`0600`, DRBD 9 문법: `auto-promote no`, `node-id`), 서비스 유닛 disable과
     마운트 요구 드롭인.
  3. 메타데이터가 없을 때만 `create-md`. 리소스 기동은 `drbd.service`를 enable하고 `systemctl`로
     올린다 — 모듈 적재가 PID 1에서 일어나야 한다(4절 항목 8). 이미 떠 있으면 `drbdadm adjust`.
  4. (운영만) 양쪽 디스크가 `Inconsistent`일 때만 첫 승격, 파일시스템이 없을 때만 `mkfs`, mount 유닛
     기동, **서비스 명시적 기동**과 헬스 확인. 서비스가 떠야 `protected`에 도달한다.
- 에이전트는 도달한 단계를 잡 결과에 보고하고, `ha status`가 노드별로 보여 준다. 호스트명은 헬스
  보고의 최신값을 쓴다(복구된 시스템은 cloud-init이 호스트명을 바꾼다).
- `ha teardown <group>`: 서비스 정지 → 언마운트 → Secondary → `down` → 리소스 파일·드롭인 제거.
  **데이터와 메타데이터는 지우지 않는다.** 삭제는 [ha-h0.md](ha-h0.md) 10절의 수동 정리 절차로 한다.
  teardown이 끝나면 그룹은 `registered`로 돌아간다.
- 인벤토리 `dataDisks`, 백업 후보 제외, 리소스 파일 백업 제외.

중간 실패의 처리:

| 상황 | 처리 |
| --- | --- |
| 대기 구성 성공, 운영 구성 실패 | 흐름 `error`. 원인을 고친 뒤 `ha acknowledge` → `ha setup` 재요청. 대기 잡도 다시 나가지만 단계 확인으로 모두 건너뛴다 |
| `create-md` 성공 후 결과 보고 유실 | 결과 미확인으로 `error`. 재요청 시 메타데이터가 있으므로 `create-md`를 생략한다 |
| `mkfs` 성공 후 마운트 실패 | 재요청 시 파일시스템이 있으므로 `mkfs`를 생략하고 마운트부터 한다 |
| 한쪽만 teardown 성공 | teardown도 단계 확인으로 멱등이다. 재요청하면 남은 쪽만 실제로 수행된다 |

**검증**: 명령 순서, 실행 전 검사 거절, 단계 생략(이미 있는 메타데이터·파일시스템)을 가짜 `Runner`로
테스트. 흐름 규칙은 PostgreSQL 테스트로 확인한다 — 같은 단계의 잡 중복 생성 거절, 대기 완료 전 운영
잡 미발행, 재시작 후 이어짐. 프로토타입은 새 볼륨만 다룬다(설계서 표 6-4). 실환경에서 처음부터
구성해 초기 동기화 시간과 가용 영역 간 쓰기 지연을 잰다.

**구현 전제**: GCP·Azure 데이터 볼륨의 `by-id` 링크 확인 — 충족(2026-11-16, [ha-h0.md](ha-h0.md) 13.1절).

**디스크 참조 규칙** (13.1절 결과에서):

- `BackingDisk`는 `/dev/disk/by-id/`로 시작하는 경로만 받는다. 프레임워크가 요청에서, 에이전트가 실행 전
  검사에서 각각 거절한다. 커널 장치 이름은 다음 부팅에 다른 디스크를 가리킬 수 있다.
- `ID-LINK`는 구성할 때 인벤토리에서 한 번 골라 리소스 명세에 고정한다. 그 뒤 "같은 디스크인지"는 노드에서
  그 경로를 해석해(링크가 있는지, 가리키는 장치) 판단하고, 나중 인벤토리의 `ID-LINK` 문자열과 비교하지
  않는다. `lsblk`는 가장 짧은 링크를 고르므로 udev 규칙이 바뀌면 같은 디스크의 `ID-LINK`도 바뀔 수 있다.
- 백업 후보 제외는 데이터 디스크가 아니라 그 위의 복제 장치가 대상이다. 백업 후보는 마운트된 파일시스템이고,
  마운트되는 것은 `/dev/drbdN`이기 때문이다. 장치 번호의 major(DRBD 147)로 판별하며 이름이나 `ID-LINK` 문자열을
  비교하지 않는다(2026-11-16 정정. 처음에는 "리소스 파일의 경로를 해석해 제외"라고 적었다).

**실환경 검증**: GCP·Azure에서는 13절의 남은 항목을 함께 확인하고 커널·패키지 버전을 기록한다.

**완료 조건**: 빈 데이터 볼륨 두 개로 `ha create` → `ha setup` → `protected`까지 사람이 노드에 접속하지
않고 도달하고, 중간에 운영 잡을 실패시킨 뒤 재요청해도 재포맷이 일어나지 않는다. 연말 항목
"복제 대상 등록", "초기 동기화"가 충족된다. — **코드·테스트 충족(2026-11-16), 실환경 남음.** 흐름 규칙은
PostgreSQL 테스트로(대기 먼저, 보고가 뒷받침한 뒤에만 다음 단계, 같은 단계 재발행 없음, 재시작 뒤 이어짐, 실패 →
`error` → `ha acknowledge` → 재요청 시 같은 공유 비밀), 노드 쪽 멱등성은 명령에 반응하는 모의 노드로(재요청 시
메타데이터·포맷·첫 승격 생략, 마운트 실패 뒤 재요청은 포맷 없이 마운트부터, 거절 시 아무것도 쓰지 않음)
확인했다. `protected` 도달과 초기 동기화 시간은 실환경에서 본다.

**남은 것 (실환경)**: LINBIT DRBD 9를 설치한 대상 VM(1.1절 전제)에서

- 빈 볼륨 두 개로 `ha create` → `ha setup` → `protected`, 초기 동기화 시간과 가용 영역 간 쓰기 지연 측정.
- 운영 잡 실패 주입(예: 서비스 유닛 기동 실패) → `error` → `ha acknowledge` → `ha setup` 재요청에서 포맷·첫 승격이
  일어나지 않는지(잡 결과 `detail.steps`).
- `drbd@<리소스>.target`으로 대기·운영 재부팅 뒤 리소스가 올라오는지(상대가 꺼진 경우 포함), `create-md`가 빈
  디스크에서 TTY 없이 진행되는지.
- `ha teardown` 뒤 데이터·메타데이터가 남는지, 다시 `ha setup` 했을 때 메타데이터 생성을 건너뛰는지.
- GCP·Azure에서 [ha-h0.md](ha-h0.md) 13절의 남은 항목과 커널·패키지 버전 기록.

### H4 — 전환

- `ha_transitions`: 유형, 진행 단계, 잡 ID, 요청자·승인자, 펜싱 기록, 손실 승인, 마지막 동기화 확인
  시각, 결과. 작업 흐름 공통 규칙을 따른다.
- 장애 전환에서 프레임워크는 `failover_pending`에서 멈추고 스스로 승격하지 않는다.
- CLI: `ha switchover`, `ha failover`, `ha resume`, `ha rejoin`, `ha acknowledge`. 서비스 주소
  재지정은 완료 메시지로 운영자에게 안내한다.

전환 유형마다 승격 조건이 다르다. "강등 완료 필수"는 계획 전환에만 해당한다 — 운영 인스턴스가 멈춘
장애 전환에서는 강등 잡을 실행할 수 없다.

| 유형 | 명령 | 승격 전 필수 조건 |
| --- | --- | --- |
| 계획 전환 | `ha switchover` | 양쪽 보고가 최신이고 `Connected`·`UpToDate`. 운영 노드에서 서비스 정지 → 언마운트 → 최종 동기화 확인(양쪽 `UpToDate`, 미동기 0) → Secondary. 이 `ha-demote`가 `completed` |
| 장애 전환 | `ha failover --confirm-fenced ... --accept-data-loss` | 그룹이 `failover_pending`. 기존 운영 노드의 펜싱 기록. 대기 디스크 `UpToDate`, 역할 Secondary. 손실 가능성 승인(4절 항목 11). 강등 잡은 없다 |
| 재부팅 후 복귀 | `ha resume` | 진행 중 흐름 없음. 대상이 기록상 운영 노드. 상대 노드가 Primary가 아님(최신 보고 기준). 대상 디스크 `UpToDate` |

펜싱 기록은 단순 확인이 아니라 사실로 남긴다: `--fenced-instance <인스턴스 ID>`,
`--fence-method stop|terminate`, 확인자(요청자), 확인 시각. 펜싱된 노드는 `ha_nodes`에 표시되고
그룹은 `ha rejoin` 전까지 `protected`가 되지 않는다. 운영 규칙으로, 펜싱한 인스턴스는 `ha rejoin`
전까지 기동하지 않는다. 실수로 기동되어도 자동 승격 차단(4절 항목 2)으로 Secondary에 머물고, 단절
뒤에 쓴 데이터가 있으면 DRBD가 분할 뇌로 연결을 멈춘다.

에이전트 실행기는 각 단계가 중간에 끊겨도 안전한 순서로 짠다. 에이전트는 리스를 잃으면 작업을
멈추므로(`pkg/agent/worker`) 승격 도중 프레임워크가 끊기면 Primary로 남고 서비스가 안 뜰 수 있다.
이 상태는 헬스 보고로 드러나고 데이터는 손상되지 않는다.

**검증**: 거절·중단 조건을 빠짐없이 테스트한다 — 유형별 전제 불충족, 강등 실패·결과 미확인 시 승격 잡
없음, 펜싱 기록 없는 장애 전환 거절, 손실 승인 없는 장애 전환 거절, 다른 잡이 있을 때 흐름 시작 거절,
흐름 진행 중 백업 잡 생성 거절, 흐름이 바뀐 뒤 도착한 승격 잡의 claim·시작 거절, 양쪽 Primary 시
`error`, 남은 HA 잡이 있을 때 `ha acknowledge` 거절, 프레임워크 재시작 후 이어짐. 실환경에서 계획 전환,
운영 정지 후 장애 전환, 옛 운영 노드 재합류(자동 재동기화와 분할 뇌 두 경우), 소요 시간 측정. H0의
전환 시간은 수동 입력 시간이라 쓰지 않는다. 펜싱으로 중지한 인스턴스를 다시 시작할 때 데이터 볼륨의
`by-id` 이름이 그대로인지 함께 본다([ha-h0.md](ha-h0.md) 13절).

**완료 조건**: 연말 항목 "수동 전환"이 충족되고 전환 이력이 조회된다.

### H2 — 대기 시스템 등록

- 복구 claim 때 부팅 확인 토큰 발급(해시 저장), 복구 실행기가 표식의 `BootVerifyToken`에 기록.
- `POST /aiha/agent/restore/{recoveryId}/boot-verify`: 토큰 검증 후 **새 `systemId`로 등록**하고
  계보(원본 시스템, 백업 세트, recoveryId)를 기록. `agents.mode`의 `recovery_registration`을 쓴다.
  요청 키로 멱등하게 한다(4절 항목 14): 같은 복구 건의 재요청은 시스템을 중복 생성하지 않고, 응답이
  유실되어도 같은 키로 등록을 마칠 수 있다.
- `aiha-agent run`: 미완료 표식이면 boot-verify를 수행한다. 순서는 **새 자격을 로컬에 저장 → 표식을
  완료 상태로 전환 → 일반 동작 시작**이다. 표식은 지우지 않으며(4절 항목 13) `sh/aiha-init.sh`도
  이에 맞춘다. 복구본에 원본 자격이 남아 있더라도(1차 방어 이전의 백업) 미완료 표식이 있는 동안에는
  어떤 보고도 시작하지 않는다.
- 재조정: `/etc/machine-id` 재생성. SSH 호스트 키와 호스트명은 cloud-init이 재생성하는 것을
  관찰했으므로([open-decisions.md](open-decisions.md) 5번) 확인만 한다.
- 대기 시드 흐름: 운영 백업 세트로 `restore create` → 부팅 확인 → 새 시스템으로 `ha create`.
- [open-decisions.md](open-decisions.md) 3-1, 4번을 설계서 기준안(신규 등록 + 계보, 재생성)으로
  해소 표시한다. 3-2(`timed_out` 최종 상태)는 이 단계에서 정하지 않는다.

**검증**: 토큰 1회성·만료, 같은 키 재요청과 다른 키 재요청, 자격 저장 실패 시 표식이 미완료로 남는지,
표식 전이 단위 테스트. `aiha-init.sh`는 `bash -n`과 정적 검토만 하고 실행은 운영자가 실환경에서 한다.
시드는 기존 복구 경로를 쓰므로, 시드가 되는 클라우드는 복구가 검증된 클라우드로 한정된다(현재 AWS).

**완료 조건**: 복구된 인스턴스가 새 시스템으로 등록되어 백업을 받을 수 있고, 시드 → 복제 구성 →
전환 전체 흐름이 실환경에서 동작한다. [open-decisions.md](open-decisions.md)의 "복구된 시스템을 다시
백업할 수 없다"도 함께 해소된다.

## 6. 상태 모델

설계서에는 상태가 두 축으로 나온다. 표 4-4의 HA 그룹 상태와 표 5-3의 판정 결과이다. 둘은 이름이
겹쳐도 같지 않으므로 분리해 저장한다.

- **그룹 상태**: 전환을 지배하는 상태. 작업 흐름, 운영자 조치, 지속된 판정으로 바뀐다.
- **판정**: 평가할 때마다 새로 도출하는 값(`ok` / `attention` / `error`)과 사유.

| 그룹 상태 | 설계서 | 진입 | 바꿀 수 있는 주체 |
| --- | --- | --- | --- |
| `registered` | (추가) | `ha create`, teardown 완료 | 구성 흐름 |
| `configuring` | 구성 중 | `ha setup` | 구성·해제 흐름 |
| `syncing` | 초기 동기화 | 양쪽 리소스 기동 완료 | 평가기(→ `protected`), 해제 흐름 |
| `protected` | 보호 중 | 동기화 완료, 판정 `ok`, 펜싱된 노드 없음 | 평가기, 작업 흐름 |
| `degraded` | 성능 저하 | 연결 끊김, 재동기화, 대기 이상, 대기 노드 펜싱 중 | 평가기, 작업 흐름 |
| `failover_pending` | 장애 전환 대기 | 운영 보고 끊김 또는 운영 서비스 실패가 유예 시간 이상 지속 | 평가기(운영 회복 시 되돌림), 전환 흐름 |
| `switching` | 전환 중 | 전환 승인 | 전환 흐름 |
| `error` | 오류 | 양쪽 Primary, 흐름 실패 또는 결과 미확인 | `ha acknowledge` |

평가기는 `registered`, `configuring`, `switching`, `error`를 바꾸지 않는다. 모든 전이는 기대하는 현재
상태를 조건으로 건 UPDATE로 하므로, 평가기와 작업 흐름이 동시에 움직여도 한쪽이 다른 쪽의 결과를
덮어쓰지 않는다. 장애 전환이 끝나면 역할이 바뀌고, 옛 운영 노드가 펜싱 상태이므로 그룹은 `degraded`가
된다. `ha rejoin`과 재동기화가 끝나야 `protected`로 돌아간다.

표 5-3의 "오류"가 곧 그룹 `error`는 아니다. 복제 연결 끊김 지속은 판정 `error`이지만 그룹은
`degraded`이고, 운영 보고 끊김은 판정 `error`(원인 미확인)이지만 그룹은 `failover_pending`이다.

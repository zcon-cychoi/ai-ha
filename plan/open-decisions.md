영향을 주는 결정은 임의로 정하지 않고 보고한다" 규칙에 따라 배경·선택지·트레이드오프만
정리하고 결정은 남겨 둔다.

[data-model.md](data-model.md), [Restore.md](Restore.md)

## 1. 복구 1차 구현 대상 모드 — **해소됨: Mode A**

**결정**: Mode A(신규 인스턴스 복구). 1차년도 범위이며
[roadmap.md](roadmap.md)의 고정 시나리오를 대상으로 한다.

**근거**: system-rescue + `copytoram` 방식의 레스큐 진입과 복구·부팅이 AWS Ubuntu
인스턴스에서 **수동으로 이미 검증되었다.** GCP Ubuntu → AWS 교차 클라우드 복구도
부팅 및 SSH 로그인까지 확인되었다. 즉 복구 메커니즘 자체는 미지수가 아니며, 남은
작업은 정해진 시나리오에 대한 자동화다.

Mode B(기존 VM 제자리)는 레스큐 진입 절차를 공유하므로 나중에 붙인다.

**user-data 레스큐 진입도 검증 완료 (2026-09-14)**: `sh/setup-sysres.sh`를 EC2
user-data로 넣어 Ubuntu 24.04에서 system-rescue가 `copytoram`으로 올라오는 것을
확인했다. 복구 경로에 남은 기술적 미지수는 없다
([roadmap.md](roadmap.md) Phase 0 결과).

## 2. `InfraProvisioner` 구현체

**배경**: 복구용 인스턴스 생성은 인프라 연동/통합 관리 프레임워크의 추상화
API(SFR-CON-02, ETRI, 2026)를 호출해야 하지만 아직 사용할 수 없다
([architecture.md](architecture.md) 4.3).

**범위 축소**: 레스큐 부팅 방식이 확정되어 **볼륨 attach/detach는 필요하지 않다.**
필요한 동작은 "user-data를 주입해 인스턴스 생성 / 상태 조회 / 종료"뿐이다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 인터페이스 정의 + 수동/스크립트 생성 | 의존성 0. 복구 로직 전체를 검증 가능. **데모에 충분** | 인스턴스 생성만 수동 단계로 남음 |
| AWS 직결 구현 후 교체 | 완전 자동화 | AWS SDK 의존성 추가([Third-Party Package Policy] 절차 필요). 나중에 이중 유지 기간 |
| 인프라 프레임워크 대기 | 중복 작업 없음 | **복구 구현 전체가 블록됨**. 일정 통제 불가 |

**의견**: 인터페이스 정의 + 스크립트 생성으로 시작한다. 이건 폴백이 아니라 어댑터
경계이므로 CLAUDE.md의 "폴백 금지"에 저촉되지 않지만, AWS SDK를 넣는 시점에는 승인이
필요하다.

**확인 필요**: 인프라 프레임워크의 API 제공 시점과 스펙 공개 시점.

## 3. 복구된 OS의 에이전트 아이덴티티

**배경**: 복구된 OS는 원본의 `systemId`·`agentId`·자격증명 사본을 갖는다
([data-model.md](data-model.md) 2.3). **부팅 확인 전까지 일반 작업 수신을 차단한다는
규칙은 이미 확정**이고, 그 이후 처리가 미결정이다.

### 3-1. 신규 등록 vs 원본 승계

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 새 `systemId`로 신규 등록 | 원본과 명확히 구분. 원본이 살아 있어도 충돌 없음 | **백업 이력이 끊긴다.** 복구 전 이력을 보려면 두 시스템을 오가야 함 |
| 원본 `systemId` 승계 | 이력 연속. "이 서버"의 관점 유지 | 원본이 살아 있으면 같은 ID의 두 시스템이 존재 |
| 신규 등록 + 계보(lineage) 기록 | 구분과 연속을 모두 확보 | 모델과 조회 UI가 복잡해짐 |

**의견**: 신규 등록 + `restoredFrom` 계보 기록. 이력 조회 시 계보를 따라가면 연속성이
보이고, 원본이 살아 있는 경우(마이그레이션 검증 등)도 안전하다.

### 3-2. `bootVerification=timed_out`의 잡 최종 상태

복구 자체(`restoreOutcome=succeeded`)는 성공했는데 확인만 못 한 상태다.
`failed`로 볼지 별도 종결 상태(`completed_unverified`)로 둘지 정해야 한다.
사용자에게 "복구 실패"로 보이면 불필요하게 재복구를 시도할 수 있다.

### 3-3. 원본에 에이전트가 없었던 경우

복구된 OS에도 에이전트가 없으므로 부팅 확인 주체가 없다
([Restore.md](Restore.md) 7.3). 현재 백업 경로는 에이전트가 수행하므로 정상 흐름에서는
발생하지 않지만, 외부 도구로 만든 백업본을 가져오는 경우를 지원할지 정해야 한다.

**영향**: [protocol.md](protocol.md) 3.2, [data-model.md](data-model.md) 2.3,
[Restore.md](Restore.md) 7절.

## 4. machine-id / SSH host key 정책

**배경**: [Restore.md](Restore.md) 6절 재조정 항목.

| 항목 | 재사용 | 재생성 |
| --- | --- | --- |
| `/etc/machine-id` | systemd 저널·DHCP 식별자가 원본과 중복 | 일부 배포판에서 부팅 시 자동 재생성. 중앙 로깅의 호스트 식별이 바뀜 |
| SSH host key | 클라이언트가 경고 없이 접속 (Mode B에 유리) | **원본이 살아 있으면 키 중복 = 보안 문제.** 클라이언트 `known_hosts` 경고 발생 |

**고려**: Mode A(신규 인스턴스, 원본은 사라짐)와 Mode B(제자리 복구, 같은 서버)의
정답이 다를 수 있다. 모드별로 다르게 하거나 복구 요청 시 사용자가 선택하게 할 수 있다.

**의견**: 기본값은 Mode A = 재생성, Mode B = 재사용. 복구 요청에서 재정의 가능하게.

## 5. cloud-init 재실행 처리

**배경**: 복구된 OS에서 cloud-init이 재실행되면 재조정으로 적용한 NIC 설정을 덮어쓸
수 있다([Restore.md](Restore.md) 6절).

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| `cloud-init clean` 후 정상 재실행 | 새 인스턴스 환경(메타데이터, SSH 키, 호스트명)에 자연스럽게 적응 | 원본의 커스텀 설정 일부가 초기화될 수 있음 |
| cloud-init 비활성화 | 복구한 설정이 그대로 유지 | 새 환경 메타데이터 미반영. 클라우드 기능 일부 동작 안 함 |
| 네트워크 모듈만 비활성화 | 절충 | 배포판·버전별 설정 방법이 다름 |

**추가 고려**: 프로바이더가 바뀌면 `datasource_list` 조정도 필요하다. 엉뚱한
데이터소스를 찾느라 부팅이 수십 초 지연되는 사례가 흔하다.

**의견**: `cloud-init clean` + `datasource_list` 조정을 기본으로 하고, NIC 설정은
cloud-init이 처리하도록 맡긴다. 재조정에서 NIC를 직접 손대는 것보다 충돌이 적다.
다만 정적 IP 구성 등 원본 설정 보존이 필요한 경우를 위해 선택지를 남긴다.

**현재 (2026-10-12, 실환경 관찰)**: cloud-init은 처리하지 않는다. 재조정은 netplan의 MAC만 바꾼다.
복구된 OS는 원본 인스턴스의 `/var/lib/cloud`를 갖고 있어, 타깃에서 부팅하면 cloud-init이 **새
인스턴스로 판단해 인스턴스당 모듈을 다시 실행했다** — user-data(aiha-init.sh) 재실행으로 레스큐에
다시 들어갔고, 호스트명·SSH 호스트 키·타깃 키 페어 공개키·netplan도 다시 만들어진다. user-data
재실행은 aiha-init.sh가 이 복구의 표식을 보면 아무것도 하지 않게 막았다. 나머지는 이 항목의 결정을
따른다. 프레임워크가 인스턴스를 만들게 되면(2번) 복구 완료 후 user-data를 지우는 것이 근본 처리다.

## 6. **프레임워크 서버** DB 제품 — **해소됨: PostgreSQL**

### 먼저, 혼동하기 쉬운 구분

프로젝트에 SQLite가 등장하는 자리는 두 곳이고 **서로 다른 물건이다.**

| | 저장소 측 `catalog.db` | **프레임워크 서버 DB** |
| --- | --- | --- |
| 위치 | **백업 저장소 안** (S3/SFTP/SMB/local) | 중앙 프레임워크 서버 |
| 역할 | 백업 데이터와 함께 이동하는 이식용 색인 | 제어 평면 (잡, 실행 시도, 리스, 진행률, 전체 이력) |
| 쓰는 주체 | 에이전트 | 프레임워크 |
| 제품 | **SQLite 유지 — 이 항목의 결정 대상이 아니다** | **PostgreSQL** |

**저장소 측 SQLite는 대안이 없다.** 저장소 안에 들어가 데이터와 함께 이동해야 하므로
서버 없이 파일 하나로 읽히는 형태여야 한다. "프레임워크가 유실되어도 저장소만으로
복구 가능해야 한다"는 요구([data-model.md](data-model.md) 1.2)가 여기서 나온다.
게다가 세트별 `manifest.json`이 복구 정본이 되면서 `catalog.db`는 재생성 가능한
색인으로 비중이 더 낮아졌다.

### 결정: 프레임워크 서버 DB는 PostgreSQL

**요구사항**([data-model.md](data-model.md) 9절): 원자적 claim, 잦은 진행 보고 갱신,
전 시스템 교차 조회, 주기적 정리.

**SQLite를 징검다리로 쓰지 않는다.** 처음부터 PostgreSQL로 시작한다.

- 원자적 claim/리스 SQL을 두 번 작성하게 되고, **이것이 이 프레임워크에서 가장 틀리기
  쉬운 부분**이다.
- SQLite(단일 writer 락)와 PostgreSQL(MVCC)은 동시성 semantics가 달라, SQLite에서
  통과한 동시성 테스트가 PostgreSQL에서의 정확성을 보증하지 않는다. 제일 검증하기
  어려운 것을 두 번 검증하게 된다.
- 데모·개발 환경에서 PostgreSQL은 컨테이너 하나다. 운영 부담이라 할 것이 없다.

**규모 감각**: 실행 중인 잡 100개 기준 진행 보고만 평균 초당 10건이고, 리스 갱신·상태
전이를 더하면 늘어난다. SFR-HA-04/05(2028, 이중화)에서 프레임워크 자체의 가용성
요구가 나올 가능성이 높은데, 그때 PostgreSQL이면 다중화 경로가 열려 있다.

### 바이너리별 의존성

| 바이너리 | DB 드라이버 |
| --- | --- |
| `aiha-agent` | `modernc.org/sqlite` (순수 Go, CGO 불필요 — 레스큐 환경에 중요) |
| `aiha-framework` | PostgreSQL 드라이버만 |

프레임워크에는 SQLite 드라이버가 들어가지 않는다. 재해 가져오기(저장소만 남은 상황에서
프레임워크 DB 재구성)도 **`manifest.json`을 읽으면 되므로**(JSON) SQLite를 링크할
이유가 없다.

### 채택 (2026-09-15)

라이선스·유지보수 지표 보고와 계획 승인을 거쳐 **`github.com/jackc/pgx/v5` v5.11.0**을
채택했다. `go.mod`에 추가된 모듈은 pgx(직접)와 pgpassfile·pgservicefile·puddle(간접, 모두
MIT)뿐이다. 스키마는 패키지마다 `schema.sql`(restore·agent·job·inventory·repository)을 시작 시
적용한다. 마이그레이션 도구는 두지 않고, 바뀐 부분을 **멱등 SQL**로 같은 파일에 덧붙인다
(`ADD COLUMN IF NOT EXISTS`, `DROP COLUMN IF EXISTS` — 2026-10 `restore_jobs` 변경에서 사용).
버전 관리가 필요해지면 그때 도구를 정한다.

DB 접근은 인터페이스 뒤에 두어 테스트 대역을 끼울 수 있게 한다. 다만 이는 제품 교체를
위한 것이 아니라 테스트를 위한 것이다.

## 7. 기존 `aiha-backup` CLI의 존치

**배경**: 바이너리를 `aiha-framework` / `aiha-agent`로 분리하면 현재 CLI의 위치가
모호해진다([architecture.md](architecture.md) 3절).

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 테스트 하니스로 유지 | 프레임워크 없이 백업·복구 엔진만 단독 검증 가능. 지금까지의 개발 방식 유지 | 진입점이 셋. 같은 코드 경로의 유지보수 부담 |
| `aiha-agent`에 디버그 서브커맨드로 흡수 | 진입점 둘. 에이전트 바이너리로 수동 실행 가능 | 에이전트 바이너리가 커짐(레스큐 환경 고려 시 불리) |
| 제거 | 가장 단순 | 단독 검증 수단 상실 |

**결정 (2026-09-17): 흡수 — 구현 완료.**

`aiha-backup`을 없애고 `aiha-agent`로 합쳤다. 다만 전제가 하나 달라졌다: 백업이
프레임워크와 통신하는 정식 기능이 되므로 "디버그 서브커맨드"가 아니다. 그래서 백업
쪽을 태그로 숨기는 대신, **레스큐 환경용 경량 빌드를 태그로 만든다.**

| 산출물 | 빌드 | 크기 |
| --- | --- | --- |
| `aiha-agent` | `./aiha-agent` | ~21 MB (2026-10-13: ~23 MB) |
| `aiha-rescue` | `./aiha-agent` + `-tags rescue` | ~7.5 MB (복구 실행기 포함 후 ~12 MB) |

`rescue` 태그가 걷어내는 것: 백업 엔진, 저장소 백엔드 전부(minio-go, go-smb2,
pkg/sftp), `modernc.org/sqlite`, Echo, pgx, `config` 패키지. 복구 읽기는
[roadmap.md](roadmap.md) Phase 2대로 rclone이 하므로 레스큐에는 이 중 무엇도 필요
없다. `config`가 링크되지 않는다는 것은 **레스큐 에이전트가 저장소 자격증명을 읽을
수 없음을 링커가 보장한다**는 뜻이기도 하다(최소 권한). 레스큐가 쓰는 저장소 자격증명은 복구
claim 응답으로만 받아 tmpfs의 `rclone.conf`에 둔다.

`sh/aiha-init.sh`가 받는 바이너리도 `aiha-rescue`로 바꿨다.

## 8. 인증 방식 — **결정됨 (2026-09-17)**

클라우드 인스턴스 아이덴티티 검증과 mTLS는 뒤로 미루고, **에이전트별 자격
발급·폐기와 복구 후 재등록을 먼저 완성한다.** 아래는 확정된 구조이며, 구현은
[roadmap.md](roadmap.md) Phase 3에서 한다.

### 8-0. 자격을 용도별로 분리한다

| 자격 | 용도 | 권한·수명 |
| --- | --- | --- |
| **북향 관리용 자격** | 운영자·포털이 프레임워크 API 호출 | 허용된 관리 작업만 |
| **등록 토큰** | 백업 에이전트 최초 등록 | 등록만 허용. 예: 30분·1회 |
| **에이전트 토큰** | 등록 후 작업 수신·진행률·결과 보고 | 그 에이전트에 배정된 작업만 |
| **복구용 claim token** | 복구 환경에서 특정 복구 작업 인수 | 지정된 `recoveryId` 한정, 짧은 TTL·1회 |

**등록 토큰으로 백업 명령을 내리거나, 에이전트 토큰으로 다른 에이전트를 등록할 수
없어야 한다.** SFR-API-03의 Keycloak SSO·RBAC은 통합 *사용자* 인증이므로, 그것을
도입하더라도 에이전트의 최초 등록과 개별 자격 관리는 별도로 필요하다.

**핵심 원칙: `systemId`·`agentId`는 식별자이지 인증 수단이 아니다.** 클라이언트가
기존 `systemId`를 보냈다는 이유로 그 시스템에 연결해 주면 안 된다. 연결 대상은
**등록 토큰에 부여된 권한**으로 결정한다.

### 8-1. 남향 bootstrap 자격 — 등록 토큰 (TTL + 1회 사용)

등록 흐름:

1. 인증된 운영자가 프레임워크에서 등록 토큰을 발급한다.
2. 프레임워크가 토큰에 **허용된 소속·대상 시스템, 만료 시각, 사용 횟수**를 저장한다.
3. 설치된 에이전트가 HTTPS로 등록 토큰을 제출한다(`POST /aiha/agent/register`).
4. 프레임워크가 토큰을 검증하고 `agentId` + 에이전트 전용 토큰을 발급한다.
5. 에이전트가 자격을 저장하고 이후 통신에 사용한다.

**토큰 사용 처리와 에이전트 생성은 하나의 DB 트랜잭션**으로 묶어 동시 등록을 막는다.
등록 응답 유실은 초기 구현에서 **미완료 등록을 폐기하고 토큰을 재발급하는 관리
경로**를 두는 정도로 처리한다.

에이전트 토큰의 형태 — JWT나 인증서 없이 시작한다:

- `crypto/rand` 32바이트 이상의 난수 Bearer 토큰.
- 프레임워크 DB에는 **원문이 아니라 SHA-256 해시**를 저장한다. 충분한 난수성을 가진
  토큰에 대한 방식이며 사용자 비밀번호 저장(bcrypt 등)과는 다르다.
  → `pkg/framework/token`의 `New`/`Hash`/`Matches`로 구현했다(등록·에이전트·claim·리스·보고 토큰 공용).
- 에이전트 쪽은 전용 자격 파일에 `root` 소유 · `0600` (`/var/lib/aiha/`).
- **토큰 확인과 작업 소유권 확인을 함께 한다.** 에이전트 A가 인증에 성공했더라도
  B의 작업을 조회하거나 B의 결과를 제출할 수 없어야 한다.
- 토큰 원문을 **로그와 URL 쿼리에 남기지 않는다.** 요청 로거가 URI를 기록하므로
  토큰은 반드시 헤더나 본문으로만 받는다.

### 8-2. 북향 임시 인증 — 남향과 분리된 관리자 API 토큰

개발용으로 남향과 **분리된** 관리자 API 토큰을 둔다. 호출 주체와 권한을 인증
미들웨어에서 구성하도록 만들어 두면, 나중에 Keycloak 검증으로 교체하면서 API의 권한
검사 로직을 그대로 유지할 수 있다.

**구현됨 (2026-11-03)**: `AIHA_FRAMEWORK_ADMIN_TOKEN_FILE`. 미설정이면 관리 API를 열지 않는다.
상세는 [protocol.md](protocol.md) 4.7.

### 8-3. 회전 — 초기에는 수동 재발급부터

| 지금 정의할 것 | 이후 확장 |
| --- | --- |
| 등록 토큰 TTL·1회 사용 | 클라우드 인스턴스 아이덴티티 추가 검증 |
| 에이전트별 토큰 발급·**폐기** | 정기 자동 회전 |
| 관리자에 의한 자격 재발급 | mTLS |
| 복구 후 새 자격 등록 | 고도화된 자격 관리 정책 |

자동 회전을 미루더라도 **폐기된 토큰을 즉시 거부하는 기능과 재등록 경로는 있어야
한다.** 자동 회전을 넣을 때는 새 토큰을 저장하고 **사용을 확인한 뒤** 기존 토큰을
만료시켜야 통신 장애로 에이전트가 끊기지 않는다.

### 8-4. 복구된 OS의 자격 교체 — 3번과 직결

**주기적인 토큰 회전으로는 해결되지 않는다.** 백업 안에 유효한 자격이 들어 있으면
원본과 복구본이 같은 에이전트로 접속할 수 있기 때문이다. 방어는 두 겹이다.

1. **자격 파일을 애초에 백업에서 제외한다** — 2026-09-17 구현됨.
   `PartitionSource.Excludes`가 OS 루트 백업에서 `/var/lib/aiha/`의 내용을 제외하고,
   그 사실을 세트 매니페스트의 `excludedPaths`에 기록한다.
2. 과거 백업에 이미 포함된 경우를 위해 **복구 시 제거도 유지한다.** 제거는 대상 OS의
   에이전트 서비스가 실행되기 **전에** 이뤄져야 한다. (미구현 — 1번 제외가 들어간 뒤의 백업만
   다루므로 지금은 필요 없다. 대신 복구 표식이 복구된 OS의 에이전트를 멈춘다.)

복구 목적에 따라 원본 자격의 처리가 갈린다.

| 복구 목적 | 원본 자격 처리 |
| --- | --- |
| 테스트 복구·복제 | 원본 자격 유지, 복구본은 별도 등록 |
| 원본을 대체하는 DR 전환 | 전환 시점에 원본 자격 폐기, 복구본은 새 자격 |

복구용 claim token으로 받은 자격은 **그 복구 작업에만** 한정하고, 복구 후 상시
백업에 쓸 자격은 **별도로 발급**한다.

## 9. 마이그레이션 협력 방식 (대외)

**배경**: SFR-HA-08~14는 문서상 ETRI 담당이나 제트컨버터클라우드가 협력하기로 합의된

| 선택지 | 우리 쪽 작업 | 비고 |
| --- | --- | --- |
| 1. ETRI 방식 기반, 우리가 보조 | 플랫폼 정보 등 입력 제공, 부분 기능 | 우리 백업/복구 자산 활용도 낮음 |
| 2. 우리 방식 기반, ETRI가 보조 | **복구 Mode A가 그대로 인프라 마이그레이션 기반** | 작업량 큼. 담당 기관 기재와 어긋나 조정 필요 |
| 3. 2-way | 영역 분담 (예: 인프라는 우리, 모델/응용 변환은 ETRI) | 인터페이스 합의 필요 |

**설계상 준비**: 방식이 확정되기 전이라도 어느 안이든 수용 가능하도록 아래는 이미
반영했다.

- 복구 잡이 목표 환경을 파라미터로 받는다 (`targetPlatform`, "제자리 되돌리기"를
  전제하지 않음)
- 이력 스키마에 잡 종류 필드를 두어 `migration` 추가 가능
- `InfraProvisioner`를 클라우드 중립으로 유지
- 백업 시점에 플랫폼 정보를 수집·보관

**범위 주의**: 플랫폼 정보를 제공하는 것은 판단의 **입력**을 주는 것이지, 우리가
추천·변환 엔진을 구현할 의무를 뜻하지 않는다. 대외 문서 작성 시 이 구분을 유지한다.

**필요한 것**: 협력 방식 합의, 그에 따른 담당 범위 문서화.

## 11. 일관성 모드 개선

**배경**: 현재 백업은 `consistencyMode: live`다. `mount -B` + `remount,ro,bind`는
**그 뷰**만 읽기 전용으로 만들 뿐 원본 마운트는 계속 쓰기 가능하므로, 백업 중 변경이
그대로 보인다([data-model.md](data-model.md) 5.2).

AI 서비스는 모델 파일 쓰기나 DB가 돌고 있을 수 있어 실무상 중요하다.

**주의**: 이것은 바인드 마운트를 없애자는 뜻이 아니다. 읽기전용 바인드는 **보호**
장치로서 제 역할을 하며(atime 갱신 차단, 커널 강제 쓰기 차단, 하위 마운트 배제,
고정 작업 경로 — [data-model.md](data-model.md) 5.5), **일관성**은 별개 문제다.
아래 어느 방식을 택하든 **스냅샷 대상 위에 같은 방식으로 바인드를 얹는 형태**가 된다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 현행 유지 (`live`) + 경고 기록 | 구현 없음. 정직한 표기 | 일관성 미보장 |
| LVM 스냅샷 | 파일시스템 일관성 확보 | LVM 구성에서만 가능. 여유 공간 필요 |
| 클라우드 볼륨 스냅샷 | 가장 안정적 | 클라우드별 API 필요. 인프라 프레임워크 의존 |
| `fsfreeze` | 표준 도구 | 동결 중 I/O 정지. 시간 제약 |

**의견**: 2026 범위는 `live` + `warnings` 정직 기록. 개선은 별도 항목으로 분리하되,
**`consistencyMode` 필드를 지금 모델에 넣어 두어** 나중에 스키마 변경 없이 확장한다.

## 12. `Target` 종류의 구현 범위

**배경**: [data-model.md](data-model.md) 5.1에서 `filesystem` / `path` /
`blockDevice` / `container`로 확장 지점을 잡았으나, 이번에 무엇을 구현할지는 별개다.

SFR-HA-01이 "모델·응용 및 운영 데이터"를 언급한다고 해서 **별도의 `path` 백업이나
컨테이너 백업 구현이 곧바로 필수인 것은 아니다.** 해당 데이터가 들어 있는
파일시스템을 통째로 백업하는 것으로 충족되는 범위가 있다.

| 선택지 | 비고 |
| --- | --- |
| `filesystem`만 구현 | 현행 개칭. 대부분의 VM 백업 요구 충족 |
| `filesystem` + `path` | 대용량 데이터 디스크에서 일부만 백업하는 요구에 대응 |
| 컨테이너까지 | velero 연동([backup.md](backup.md)). 별도 작업량 |

**필요한 것**: 실제 사용 시나리오에서 파일시스템 단위 백업으로 부족한 경우가
있는지 확인.

## 13. 에이전트 바이너리를 레스큐에 전달하는 방식 — **해소됨 (2026-09-16)**

**결정**: `sh/aiha-init.sh`가 Ubuntu 단계에서 `AGENT_URL`로 내려받아 **SHA-256을 검증한 뒤**
`/autorun/aiha/aiha-rescue`에 설치한다. 복구 정보(`/autorun/aiha/recovery.env`)도 같은 디렉터리에
둔다. 자동 실행 스크립트 `/autorun/autorun2`는 인스턴스마다 같으므로 **이미지(sysres.tar)에 넣는다**
— 원본은 `sh/autorun2` (2026-10-12).

**근거**: `/autorun`은 sysres.tar가 만드는 디렉터리이고, 레스큐 부팅 시 `copytoram`이 램으로
올려 주며 SystemRescue가 `autorun0..9`를 차례로 자동 실행한다(서비스로 실행되어 PATH가 짧으므로
`autorun2`가 `/etc/profile`을 읽는다. 한 스크립트가 실패하면 뒤의 것은 실행되지 않는다). 그래서

- 레스큐에서 **복구 대상 디스크를 마운트할 필요가 없다** — 마운트·언마운트와 그 실패 처리가
  모두 사라졌다(이전 `sh/aiha-rescue-start.sh`는 삭제)
- 에이전트를 레스큐에서 내려받지 않는다 — 이미지에 URL을 박아 둘 이유도 없다
- 에이전트를 고쳐도 **이미지를 다시 만들 필요가 없다**

**sysres.tar 해제 뒤에 설치한다 (2026-10-12 정정).** 처음에는 "해제 전에 설치해도 디렉터리만
겹치고 파일은 남는다"고 보았으나, tar 해제는 같은 이름의 일반 파일을 덮어쓴다. aiha-init.sh가
만들던 `autorun2`가 이미지의 것으로 바뀐 것을 실환경에서 확인했다. 그래서 `setup-sysres.sh`를
재부팅 없이 호출하고, 파일을 설치한 뒤 aiha-init.sh가 재부팅한다. 같은 일을 계기로 `autorun2`는
이미지 쪽에 두기로 했다 — 내용이 인스턴스마다 바뀌지 않는다. 이미지 안 `autorun0`·`autorun1`은
autorun2보다 먼저 실행되므로, `/autorun/aiha/aiha-rescue`를 덮어쓰지 않는지, 오래 멈춰
autorun2를 막지 않는지 확인한다.

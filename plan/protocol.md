## 1. 남향 프로토콜: 아웃바운드 롱폴링

### 1.1 방향 결정

**에이전트가 프레임워크로 아웃바운드 HTTPS 연결만 한다.** 대상 VM에는 인바운드
포트를 열지 않는다.

대안이었던 "에이전트가 VM마다 API 서버를 열고 프레임워크가 호출"을 채택하지 않은
이유:

- **도달성** — 에이전트는 여러 클라우드의 고객 VPC 안에 있다. 프레임워크가 각 VM으로
  들어가려면 모든 VM에 인바운드 SG 규칙, 공인 IP 또는 VPN/피어링이 필요하다.
  멀티 클라우드에서 이 부담은 급격히 커진다.
- **레스큐 환경** — 복구용 인스턴스는 system-rescue로 부팅되며, 프레임워크는 그
  주소를 미리 알 수 없다. 그래서 [Restore.md](Restore.md)의 복구 흐름은 **이미
  에이전트 발신 콜백**이다. 백업만 반대 방향이면 두 경로의 인증·재시도·장애처리를
  이중으로 만들어야 한다.
- **큐를 어차피 만들게 된다** — VM이 재부팅 중이거나 네트워크가 끊긴 순간
  프레임워크의 push는 실패한다. 그러면 재시도 + 대기열을 결국 구현해야 한다.
  인바운드 방식은 "큐 + 도달 불가 처리 + 인바운드 포트 개방"을 전부 하고,
  아웃바운드 방식은 "큐"만 하면 된다.
- **공격 표면** — 모든 백업 대상 VM이 명령 실행 API를 노출하는 구조 자체가 위험하다.

동일 문제를 푸는 선례가 모두 아웃바운드다: AWS Systems Manager Agent는 모든 연결을
에이전트에서 시작해 대상 인스턴스에 인바운드 허용이 필요 없도록 설계되어 있다.
GitHub Actions self-hosted runner, GitLab Runner, Buildkite Agent, Teleport도 같다.

### 1.2 지연 특성

롱폴링은 주기적 폴링(interval polling)이 아니다. 에이전트가
`GET /aiha/agent/jobs?wait=45s`를 보내면 프레임워크는 응답을 **붙잡은 채로 대기**하고,
잡이 생성되면 이미 열려 있는 그 연결로 전달한다.

다만 전달 지연을 RTT와 동일시하면 부정확하다. 실제로는 다음이 더해진다.

- 프레임워크의 잡 생성 → 대기 중인 폴에 통지되기까지의 서버 내부 처리
- 큐 조회 및 DB 접근
- **claim 왕복** — 에이전트는 잡을 받은 뒤 claim이 성공해야 실행을 시작한다(2.3절)

그래도 전체가 초 단위 이내이고, 백업 잡은 분~시간 단위로 수행되므로 실무상 무의미한
차이다. 게다가 대부분의 백업은 예약 실행이라 프레임워크가 시점을 미리 알고 있다.

### 1.3 내구성은 롱폴링이 아니라 잡 영속화에서 나온다

"롱폴링이라 유실이 불가능하다"는 표현은 과장이다. 정확히는 다음 세 가지가 함께
성립할 때 응답 유실을 견딜 수 있다.

1. **잡을 영속 저장한다** — 잡은 메모리 이벤트가 아니라 프레임워크 DB의 행이다.
2. **원자적으로 점유한다** — claim은 DB에서 원자적으로 처리한다(2.3절).
3. **재전달한다** — 점유되지 않았거나 리스가 만료된 잡은 다시 전달 대상이 된다.

롱폴 응답이 네트워크에서 유실되어도 잡은 여전히 `queued`이므로 다음 폴에 다시 나간다.
전달 자체는 최소 1회(at-least-once)이며, **중복 실행을 막는 책임은 2절의 작업 실행
계약에 있다.**

### 1.4 생존 판단

폴 연결이 열려 있다는 사실은 **참고 신호**이지 생존의 정의가 아니다. HTTP/2
멀티플렉싱, 중간 프록시, 하프오픈 연결 때문에 연결 상태와 실제 생존은 어긋날 수 있다.

생존은 **마지막 정상 통신 시각(`lastSeenAt`)** 으로 판단한다. 자세한 규칙은 2.4절.

또한 `online`을 곧바로 "정상적으로 보호 중"으로 표시해서는 안 된다. 에이전트가 살아
있어도 작업은 멈춰 있을 수 있다.

### 1.5 운영 파라미터

| 항목 | 값 / 지침 | 이유 |
| --- | --- | --- |
| `wait` 창 | 30~45초 (시작값) | ALB 기본 idle timeout이 60초. 배포 시 **중간 프록시와 클라이언트 timeout까지 함께** 맞춰야 한다 |
| 서버 write timeout | `wait`보다 충분히 길게 | 짧으면 대기 중인 폴을 서버가 끊는다 |
| 서버 read header timeout | 짧게 (수 초) | slowloris 방어. 헤더 수신은 대기 대상이 아니다 |
| 동시 대기 요청 수 | **에이전트 수에 비례** | 실제 TCP 연결·고루틴 수는 HTTP 버전과 구현에 따라 다르다. `ulimit -n`과 프록시의 동시 연결 한도를 함께 확인 |
| 폴 재요청 | keep-alive 재사용, 즉시 재요청 | 핸드셰이크 반복 회피 |
| 백오프 | **연결 실패·429·일시적 5xx에만** 지수 백오프 + jitter | 정상 `wait` 타임아웃은 백오프 대상이 아니다 |

### 1.6 엔드포인트

모두 에이전트 → 프레임워크 방향이다.

| 메서드 | 경로 | 용도 | 구현 |
| --- | --- | --- | --- |
| POST | `/aiha/agent/register` | 에이전트 등록, `agentId` 및 상시 자격 발급 | ✅ 2026-09-17 |
| GET | `/aiha/agent/jobs?wait={sec}` | 잡 대기 (롱폴링). 잡이 있으면 즉시, 없으면 `wait` 후 204 | ✅ 2026-09-17 |
| POST | `/aiha/agent/jobs/{jobId}/claim` | 잡 점유 확정 → `attemptId` + `leaseToken` 발급 | ✅ 2026-09-17 |
| POST | `/aiha/agent/jobs/{jobId}/progress` | 진행·생존 보고 및 리스 갱신. 응답으로 취소 지시 수신 | ✅ 2026-09-17 |
| POST | `/aiha/agent/jobs/{jobId}/result` | 실행 결과 보고 | ✅ 2026-09-17 |
| POST | `/aiha/agent/inventory` | 보호 대상 구성 정보 보고 (파티션). 2.7절 | ✅ 2026-09-18 |
| POST | `/aiha/agent/restore/{recoveryId}/claim` | 레스큐 에이전트의 복구 준비 완료 신고 및 플랜 수령 | ✅ M1 |
| POST | `/aiha/agent/restore/{recoveryId}/progress` | 레스큐 에이전트의 복구 진행 보고 (단계 n/6, 읽은 바이트). `reportToken` 인증 | ✅ 2026-10-08 |
| POST | `/aiha/agent/restore/{recoveryId}/result` | 레스큐 에이전트의 복구 결과 보고. `reportToken` 인증 | ✅ 2026-10-08 |
| POST | `/aiha/agent/restore/{recoveryId}/boot-verify` | 복구된 OS의 부팅 확인 보고 | 🚧 501 |
| POST | `/aiha/agent/health` | 이중화 노드 헬스 보고, 응답으로 HA 배정 수신. 2.8절 | ✅ 2026-11-09 |

롱폴은 대기하는 동안 **3초마다** 큐를 확인한다. 새 잡이 에이전트에 닿기까지 최대 3초가
걸리지만, 백업이 몇 초 늦게 시작하는 비용은 없고 더 자주 확인하면 유휴 에이전트 수만큼
인덱스 조회가 늘어난다. 규모가 커지면 PostgreSQL `LISTEN/NOTIFY`로 지연과 부하를 함께
없애는 것이 다음 단계다.

`wait`는 서버에서 **[5s, 45s]로 클램프**한다. 하한이 있는 이유는 `wait=0`이면 인증에
성공한 에이전트가 즉시 204를 무한 반복해 사실상 회전할 수 있기 때문이다. IP 단위
레이트 리밋은 인증 미들웨어보다 바깥에 있어 **인증 실패**를 막아 주지만, 정상 자격의
회전은 막지 못한다.

롱폴은 서버의 쓰기 타임아웃(30s)보다 오래 응답을 붙잡으므로, 해당 요청에 한해
`http.NewResponseController`로 쓰기 데드라인을 연장한다. 전역 타임아웃은 그대로 둔다 —
그것은 연결만 열어 두고 멈춘 상대를 떨구기 위한 것이다. 클라이언트 쪽도 같은 이유로
용도별 타임아웃을 쓴다(등록 30s, 롱폴은 `wait` + 여유).

`GET /jobs`와 `POST /claim`을 분리하는 이유: 롱폴 응답이 유실되어도 잡이 `claimed`로
잘못 넘어가지 않게 하기 위해서다. 응답을 실제로 받은 에이전트만 claim을 보낸다.

`restore/*` 엔드포인트의 인증은 일반 잡과 다르다(claim은 claim 토큰, progress·result는 claim이
발급한 보고 토큰, boot-verify는 부팅 확인 토큰). 레스큐 에이전트도, 복구된 OS도
정상 등록된 시스템이 아니기 때문이다 — 4.7절과 [Restore.md](Restore.md) 참조.

## 2. 작업 실행 계약

**이 절의 규칙은 전송 방식과 무관하다.** 나중에 SSE나 gRPC로 바꾸더라도 리스, 실행
시도, 멱등성은 그대로 유지되어야 한다. 전송 계층 추상화(1절)가 감출 수 있는 것은
HTTP·롱폴 타임아웃·재시도 같은 관심사뿐이다.

### 2.1 식별자

| 필드 | 역할 |
| --- | --- |
| `jobId` | 사용자가 요청한 **논리적 작업**. 수명 내내 불변 |
| `attemptId` | 해당 작업의 **개별 실행 시도**. claim마다 새로 발급 |
| `leaseToken` | 현재 실행 시도의 **권한 증명** |
| `seq` | 해당 실행 시도 안에서의 **보고 순서** (단조 증가) |

claim 성공 시 실행 시도와 리스를 함께 발급하고, **진행·완료 보고는 모두 그 실행
시도에 귀속시킨다.** 서버는 이전 실행 시도의 보고가 현재 상태를 바꾸지 못하게 한다.

### 2.2 리스 만료는 기존 실행의 종료가 아니다

이것이 이 프로토콜에서 가장 주의해야 할 지점이다. 다음 상황이 가능하다.

1. 에이전트가 백업을 수행 중이다.
2. **프레임워크와의 통신만** 끊긴다. 디스크 읽기와 저장소 업로드는 계속된다.
3. 프레임워크가 리스 만료로 잡을 `queued`로 되돌린다.
4. 새 실행이 시작되어 기존 실행과 겹친다.
5. 늦게 도착한 기존 실행의 완료 보고가 새 실행 상태에 영향을 준다.

`attemptId` + `leaseToken`은 **5번(상태 오염)만** 막는다. **토큰 검사는 옛 프로세스의
디스크 읽기나 저장소 업로드를 멈추지 못한다.** 따라서 별도 정책이 필요하다.

| 정책 | 내용 |
| --- | --- |
| 에이전트 측 상호배제 | 동일 보호 대상에 대해 에이전트가 동시에 두 실행을 시작하지 않는다 (로컬 락) |
| 리스 갱신 실패 시 중단 | 진행 보고가 연속 실패해 리스 갱신에 실패하면 **에이전트가 스스로 실행을 중단**한다. 무한정 계속 쓰지 않는다 |
| 시도별 산출물 분리 | 백업 산출물을 실행 시도별로 분리하고, **유효한 실행만 최종 백업본으로 확정**(커밋)한다 |
| 자동 재실행 제한 | 기존 실행의 중단을 확인할 수 없으면 자동 재실행하지 않는다 |

**프로토타입 방침**: 실행 중 백업의 리스 만료 후 **자동 재실행을 하지 않는다.**
`failed`(사유: 통신 두절, 결과 미확인)로 종료하고 사용자가 다시 요청하게 한다.
위 정책이 전부 갖춰진 뒤 자동 재시도를 켠다. 구현과 검증이 훨씬 단순하다.

#### 현행 코드와의 관계

- **시도별 산출물 분리는 이미 부분적으로 성립한다.** `pkg/backup/model/model.go`의
  `BackupFileName`이 호출마다 랜덤 ID를 붙이므로, 두 시도는 서로 다른 파일에 쓴다.
  없는 것은 **커밋 단계**(어느 시도의 산출물이 정본인지 확정)와 **버려진 시도의 정리**다.
- **버려진 시도는 조용히 저장 공간을 먹는다.** 특히 S3는 `pkg/backup/repository/sink_s3.go`가
  multipart upload를 쓰므로, 중단된 시도가 남긴 **미완료 multipart는 일반 목록 조회에
  보이지 않으면서 과금된다.** 에이전트의 `Abort()` 경로가 닿지 못하는 경우(프로세스
  강제 종료, VM 정지)를 대비해 **버킷에 미완료 multipart 자동 중단 lifecycle 규칙을
  두는 것을 운영 필수 항목으로 한다.**
- 로컬/SFTP/SMB 백엔드는 부분 파일이 남으므로, 커밋되지 않은 시도의 산출물을 정리하는
  주기적 GC가 필요하다.

### 2.3 claim

**claim은 DB에서 원자적으로 처리하고, claim 성공을 확인한 뒤에만 실행을 시작한다.**
잡을 롱폴 응답으로 받았다는 것만으로는 실행 권한이 없다.

멱등성 범위에 주의한다. "같은 에이전트면 기존 리스를 반환"은 범위가 너무 넓다.
동일 에이전트의 오래된 요청이 새 실행 시도에 섞일 수 있다. **동일 claim 요청 키에
대한 재요청**으로 한정한다.

| 상황 | 응답 |
| --- | --- |
| 미점유 잡에 대한 최초 claim | 새 `attemptId` + `leaseToken` 발급 |
| **같은 claim 요청 키**의 재요청, 아직 보고 전 | **기존 `attemptId` + 새 `leaseToken`** (아래 참고) |
| **같은 claim 요청 키**의 재요청, 이미 보고함 | 409 거부 |
| 다른 claim 요청 키 / 다른 에이전트, 유효 리스 존재 | 409 거부 |
| 리스 만료된 잡 (자동 재실행 허용 시) | 새 `attemptId` 발급, 이전 시도는 `superseded` 표시 |

#### 구현 (2026-09-17): 재요청에는 리스 토큰을 새로 발급한다

위 표의 원래 문구는 "기존 `leaseToken` 반환"이었으나 그대로는 구현할 수 없다. **프레임워크는
리스 토큰의 해시만 저장하므로 원문을 되돌려 줄 수 없다.** 처음에는 재요청에도 새 토큰을
만들어 돌려주되 저장된 해시는 그대로 두는 형태였고, 이 경우 **재요청 claim은 "성공"하지만
받은 토큰으로 보내는 모든 진행 보고가 거부되어 에이전트가 스스로 중단하고 잡이 실패한다.**
테스트로 확인한 실제 결함이다.

그래서 재요청에는 **같은 시도에 새 토큰을 발급하고 저장된 해시를 교체**한다. 응답을 잃은
에이전트는 첫 토큰을 본 적이 없으니 잃는 것이 없다.

단 **그 시도가 아직 한 번도 보고하지 않았을 때만** 교체한다. 보고가 있었다는 것은 에이전트가
토큰을 받아 이미 일하고 있다는 뜻이고, 그 뒤에 도착한 같은 키의 claim은 늦게 도착한
중복이다. 이때 교체하면 **실행 중인 시도의 토큰이 무효가 되어 백업 도중 스스로 중단한다.**
`last_seq = 0` 조건이 이것을 막는다.

### 2.4 생존 보고와 진행량 분리

**작업 진행량이 변하지 않아도 일정 주기로 생존 및 리스 갱신 보고를 보낸다.**
"큰 파티션은 느리니 리스를 길게 잡는다"는 무응답과 느림을 구분하지 못한다.

별도 heartbeat API는 만들지 않는다. 기존 `/progress`에 같은 진행량을 주기적으로
보내면 된다. 단 **백업 처리 루프가 멈춰 있어도 보고 루프는 동작해야 한다.**
보고 루프를 처리 루프와 같은 고루틴에 두면 이 성질이 깨진다.

시작값 예시(확정값 아님). 서버가 claim 응답에 실어 내려주어 에이전트 재배포 없이
조정할 수 있게 한다.

| 항목 | 시작값 |
| --- | --- |
| 작업 중 보고 주기 | 10초 |
| 작업 리스 | 90초 |
| 유휴 상태 롱폴링 `wait` | 45초 |
| 에이전트 offline 판단 | 마지막 정상 통신 후 120초 |

세 시각을 **구분해서** 저장한다.

| 필드 | 의미 |
| --- | --- |
| `lastSeenAt` | 에이전트와 마지막으로 정상 통신한 시각 |
| `leaseExpiresAt` | 특정 작업의 실행 권한 만료 시각 |
| `lastProgressAt` | 실제 처리량이나 단계가 마지막으로 바뀐 시각 |

`lastSeenAt`은 갱신되는데 `lastProgressAt`이 오래 정체하면 "에이전트는 살아 있으나
작업이 멈춤"이다. 이는 통신 두절과 다른 장애이고 다른 조치가 필요하므로 사용자에게
구분해서 보여준다.

### 2.5 멱등성 계약

불안정한 링크에서 모든 보고가 재시도된다(CLAUDE.md의 "재시도는 멱등 연산만").

| 연산 | 보장 방식 |
| --- | --- |
| 잡 claim | 2.3절. claim 요청 키 기준 |
| 진행 보고 | `attemptId` + 단조 증가 `seq`. 과거 `seq`는 무시. 만료·불일치 리스는 거부 |
| 결과 보고 | `attemptId` 기준 1회 반영. 이미 종료 상태면 **같은 결과일 때 200, 다르면 409** |
| 에이전트 등록 | 클라이언트 생성 idempotency key |
| 복구 claim | 아래 참조 |
| 부팅 확인 | 1회용 부팅 확인 토큰 + 동일 키 재요청 시 기존 결과 반환 |

#### 복구 claim의 멱등성

**"1회용 토큰이 소인되므로 자연히 1회"는 멱등성 보장이 아니다.** 그것은 중복 사용
제한일 뿐이다. 서버가 토큰을 소인한 직후 응답이 유실되면 **에이전트는 복구 플랜을
받지 못한 채 재요청도 거부되어 영구 대기한다.**

필요한 계약:

- 최초 성공 시 **토큰 소인, 실행 시도 생성, 응답 정보 저장을 원자적으로** 처리한다.
- **동일 인증 주체 · 동일 요청 키 · 동일 요청 내용**의 재요청에는 저장된 기존 응답을
  그대로 반환한다.
- 같은 키로 다른 내용을 요청하거나 다른 주체가 재사용하면 거부한다.
- 응답에 이후 진행·결과 보고에 사용할 **복구 전용 자격**을 함께 발급한다.

**M1 구현 (`pkg/framework/restore`)**: 응답을 따로 저장하지 않는다. 재요청에는 잡 데이터로
응답을 다시 만들고, 대신 **claim 이후 플랜·저장소 정보를 바꾸지 않아** 같은 키가 같은 내용을
받게 한다. 같은 키의 재수신은 **재수신 기한**(`AIHA_FRAMEWORK_CLAIM_REDELIVERY`, 기본 10m)
안에서만 허용하고, 지나면 410으로 거부한다. 최초 claim은 `claim_expires_at` 이전에만 된다.
claim 성공 시 상태는 `restoring`이 아니라 `claimed`다(3.2). 복구 전용 자격은 2026-10-08부터
발급한다(아래). 저장소 자격증명은 복구 잡에 저장하지 않는다(2026-10-12) — 잡은 등록된 저장소의
ID만 갖고, claim 응답을 만들 때 저장소 등록에서 복호화해 싣는다. 복호화는 claim을 기록하기
전에 하므로, 실패하면 상태가 바뀌지 않고 같은 요청을 다시 보내면 된다. 백업 잡 claim도 같다:
`AgentJobClaimResp.repository`에 잡이 쓸 저장소가 자격증명과 함께 실린다.

**복구 전용 자격 (2026-10-08)**: claim 응답에 `reportToken`을 싣는다. 프레임워크는 해시만
저장하므로 재수신 응답에 같은 토큰을 다시 줄 수 없고, **재수신 때마다 새로 발급해 이전
것을 대체한다**(백업 잡 claim 재요청의 리스 토큰 재발급과 같은 규칙). 에이전트는 이를
tmpfs의 `report.token`에 두고 `Authorization: Bearer`로 `progress`·`result`를 보낸다.

- `progress`: `seq` 단조 증가, 과거 `seq`는 받아들이되 무시한다. 첫 보고에 `claimed → restoring`.
  종료된 잡이면 409. 보고 실패는 복구를 멈추지 않는다 — 포맷 이후 중단이 더 위험하다
- `result`: `succeeded → awaiting_boot`, `failed → failed`. 단 **`preparing` 단계의 실패는
  디스크를 바꾸지 않았으므로 잡을 끝내지 않고 `claimed`로 되돌린다**(진행 기록·`last_seq` 초기화) —
  같은 레스큐에서 원인을 고친 뒤 같은 잡으로 다시 실행한다. 같은 결과의 재전송은 204, 다른
  결과는 409. 에이전트는 연결 실패·429·5xx만 재시도하고, 끝내 전달 못 하면 오류로 종료한다
- 실패 메시지는 단계와 원인 요약만 담는다. 도구의 stderr는 레스큐 로컬 로그에만 남긴다

### 2.6 취소 전달

취소 API만 있고 실행 중인 에이전트에 전달할 경로가 없으면 취소는 동작하지 않는다.
**`/progress` 응답에 `cancelRequested`를 실어 전달한다.** 별도 인바운드 연결 없이
다음 보고 응답에서 취소가 전달된다.

| 대상 | 처리 |
| --- | --- |
| 대기 중(`queued`) 잡 | 즉시 `cancelled` |
| 실행 중 잡 | 취소 요청 기록 → 에이전트가 안전하게 중단 → **중단 확인 후** `cancelled` |
| 에이전트 미응답 | **취소 요청만으로 중단 완료 처리하지 않는다.** `cancelling` 상태로 남기고 리스 만료 후 결과 미확인으로 종료 |
| 이중화 잡 | 거절(409). 이중화 작업 흐름과 함께 끝난다(3.4절) |

복구는 단계별로 중단 가능성이 다르다. 어느 단계에서 중단할 수 있고 중단 후 디스크가
어떤 상태로 남는지를 [Restore.md](Restore.md)에 명시한다. 특히 파티션 포맷 이후에는
중단해도 원래 상태로 돌아가지 않는다.

백업 상태머신에도 `cancelled`가 있으므로 백업용 취소 API도 제공한다.

### 2.7 인벤토리 — 백업 대상 결정 (2026-09-18 구현)

프레임워크는 보호 대상의 디스크 구성을 스스로 알 수 없다. 그래서 백업잡을 만들 때
파티션을 손으로 나열해야 했고, 그것이 **대상을 잘못 고를 수 있는 유일한 경로**였다.
`POST /aiha/agent/inventory`는 에이전트가 자기 시스템의 구성을 보고해 그 경로를 없앤다.

이 기능의 목적은 "장치를 고른다"가 아니라 **"고르지 못했을 때 그것을 알아차린다"**이다.
조용히 빠진 파티션은 복구 시점에야 드러나고, 그때는 원본이 없다.

#### 무엇을 보고하는가 — 축약 모델

에이전트가 백업마다 수집하는 `SystemInfo` 전체를 보내지 않는다. 거기에는 `/etc/netplan`
원문이 들어 있고 무선 passphrase 같은 **비밀이 섞일 수 있다.** 그것은 에이전트가 관리하는
백업 매니페스트에 있을 것이지 프레임워크 DB에 복제할 것이 아니다. 보고 모델은 파티션
목록(장치·마운트 지점·fsType·fsUUID·크기)과 플랫폼 요약만 담아, **비밀을 구조적으로 담을
수 없게** 한다.

시스템별로 **한 행**만 보관한다. 레이아웃의 이력은 백업 매니페스트가 캡처 시점마다
기록하고 있고, 복구가 필요로 하는 형태도 그쪽이다.

`collectedAt`(에이전트가 읽은 시각)과 `reportedAt`(프레임워크가 들은 시각)을 **나눠서**
저장한다. 제때 보고하지만 낡은 값을 보내는 에이전트와 연락이 끊긴 에이전트는 다른
고장이고, **없어진 파티션을 잡에 넣을 수 있는 것은 전자뿐**이다.

#### 장치 경로는 마운트 테이블에서 그대로 쓸 수 없다

클라우드 이미지는 루트 파일시스템을 `/dev/root`로 보고한다. 그 값은 `--device`로 되돌려
쓸 수 없으므로, **마운트의 `major:minor`로 `/sys/dev/block`을 조회해 정규 경로를 얻는다.**
`pkg/backup/source`의 `mountPointOf`가 같은 이유로 이미 장치 번호 대조를 쓴다.

같은 파일시스템이 여러 번 마운트되면 **`Root == "/"` 중 마운트 지점이 짧은 것**을 대표로
삼는다. 등장 순서로 고르면 바인드 마운트가 대표가 될 수 있다.

#### "시스템 백업"의 기본 포함 범위

**현재 마운트되어 있고 이 에이전트가 아카이빙할 수 있는 로컬 파일시스템 전부**다.
1차년도 고정 시나리오에는 데이터 디스크나 로컬 백업 저장소가 없으므로 그것을 제외하는
규칙은 만들지 않는다 — 만들면 [data-model.md](data-model.md) 4.7의 Tier 판정을 앞당겨
들여오게 된다.

Btrfs는 자동 선택 후보에서 제외한다. 파티션 소스는 마운트 지점을 바인드할 뿐이어서
마운트된 서브볼륨만 잡히고, 서브볼륨 처리는 [roadmap.md](roadmap.md) 3.2에서 1차년도
범위 밖이다.

#### 후보(`candidate`)와 선택 가능(`selectable`)은 다르다

백업할 수 없는 파티션도 **사유와 함께 목록에 남긴다.** 없어진 것과 일부러 뺀 것을
운영자가 구분할 수 있어야 하기 때문이다. 그래서 검증은 "목록에 있는가"로 끝나면 안 된다 —
목록에 있다는 것이 곧 허가가 되어 버린다.

| 필드 | 의미 |
| --- | --- |
| `candidate` | 자동 선택에 포함된다 |
| `selectable` | 수동으로 지정할 수 있다 |
| `reason` | 둘 중 하나가 false인 이유 |

#### 완전성 — 마운트된 것만으로는 부족하다

마운트 테이블은 **마운트된 것만** 안다. 별도 `/boot`나 ESP가 마운트 해제된 상태라면
목록에서 그냥 빠지고, 그것으로 고른 세트는 **백업은 성공하고 복구만 실패한다.**

이미 수집하는 fstab과 대조해 판정한다. 아래 중 하나라도 해당하면 `complete: false`다.

- `/`가 후보에 없다
- 후보가 0개다
- fstab이 선언한 로컬 파일시스템(`noauto`·`nofail`·pseudo 제외)이 후보에 없다

**`complete: false`인 인벤토리로는 자동 선택을 하지 않는다.** 수동 지정은 막지 않는다 —
운영자가 fstab이 모르는 것을 알 수 있다.

#### 잡 생성 경로의 검증 계약

`job.Service.CreateBackup`은 스펙이 형식에 맞는지만 본다. 어떤 파티션이 있는지는 모른다.

> **백업잡을 만드는 모든 경로는 `CreateBackup` 직전에 `inventory.Service.BackupDevices`
> 또는 `ValidateDevices`를 거쳐야 한다.** 지금은 CLI 하나, Phase 4에서는 북향 핸들러가
> 두 번째 호출자가 된다.

검증을 `job` 패키지 밖에 둔 것은 인벤토리가 아직 없는 시스템에서도 큐가 동작하게 하기
위해서다. 그것은 **의존성을 없앤 것이 아니라 계약으로 옮긴 것**이므로 여기에 적어 둔다.

#### 실행 직전 재검증

잡을 만든 뒤 실행까지 구성은 바뀔 수 있다. 생성 시 검증만으로 장치 오류를 막는다고 말할
수 없다. 에이전트는 **엔진을 시작하기 전에** 다음을 확인하고, 어긋나면 아무것도 올리지
않는다.

| 확인 | 막는 것 |
| --- | --- |
| 각 장치가 지금 마운트되어 있는가 | 없어진 장치가 세트 중간에 터져 앞선 파티션의 업로드를 낭비하는 것 |
| 잡의 `expectedFsUuids`와 현재 fsUUID가 같은가 | 경로가 재사용되어 **오류 없이 다른 파일시스템을 백업하는 것** |

fsUUID를 읽지 못한 경우는 불일치로 보지 않는다. 검사가 실행되지 못한 것과 검사가 장치를
탈락시킨 것은 다르다.

#### 예외: 인벤토리 없이 수동 지정

인벤토리가 아직 없는 시스템에 `--device`로 백업을 요청하면 **검증을 건너뛰고 진행한다.**
CLAUDE.md의 fallback 금지에 닿는 지점이므로 정책으로 명시한다.

- **필요**: 인벤토리 도착 전이나 보고 실패 상태에서도 백업은 되어야 한다. 이것이 Phase 3
  이전의 유일한 동작 방식이었고, 없애면 바로 그 상황에서 빠져나갈 길이 사라진다
- **위험**: 검증되지 않은 장치명이 통과한다
- **완화**: 위의 실행 직전 재검증이 현재 시스템을 읽어 다시 확인한다. CLI는 검증을
  건너뛴다는 사실을 출력한다

#### 데이터 디스크와 복제 볼륨 (2026-11-16 추가, [ha-roadmap.md](ha-roadmap.md) H3b)

- **`dataDisks`**: 파티션이 없고 마운트되지 않은 전체 디스크 목록이다. 복제 볼륨을 구성할 디스크를
  운영자가 노드에 접속하지 않고 고르기 위해서다. 항목은 `device`(지금의 커널 이름, 표시용),
  `byIdPath`(`lsblk`의 `ID-LINK`, `/dev/disk/by-id/…`), `sizeBytes`, `signature`(`blkid`가 찾은 것.
  빈 디스크는 비어 있고, 복제 메타데이터가 있으면 `drbd`)다. 복제 장치(`drbdN`)가 올라간 디스크도
  목록에 남는다. `ha create --primary-disk/--standby-disk`에는 `byIdPath`를 그대로 쓴다.
  `aiha-framework system inventory`가 함께 보여 준다.
- **복제 볼륨은 백업 후보가 아니다.** 장치 번호의 major가 DRBD의 147이면 후보에서 빼고 사유를 남긴다.
  그 볼륨은 이중화 그룹이 보호하고, 백업이 운영 노드에서만 읽어 복구하면 짝이 앞서간 볼륨을 되돌리게 된다.
- **리소스 파일은 루트 백업에서 빠진다.** `/etc/drbd.d/*.res`는 공유 비밀을 담으므로 아카이브에 넣지
  않고 매니페스트 `excludedPaths`에 적는다. 복구된 시스템은 그 쌍의 일원이 아니며, 다시 복제하려면
  구성이 파일을 새로 쓴다.

### 2.8 헬스 보고 — 이중화 (2026-11-09 구현, [ha-roadmap.md](ha-roadmap.md) H1)

`POST /aiha/agent/health`. 이중화 노드가 서비스·GPU·복제 상태를 **측정만** 해서 보고하고,
프레임워크가 **판정**한다. 같은 값이라도 역할에 따라 기대값이 다르고(대기 노드의 서비스 정지는
정상, 운영 노드에서는 장애), 역할은 프레임워크의 기록이기 때문이다.

#### 응답이 배정을 전달한다

프레임워크는 노드에 접속하지 않으므로, 무엇을 점검할지는 **보고의 응답**으로 내려간다 — 역할,
서비스 정의(유닛·포트·헬스 경로·기대 GPU 수), 복제 리소스, 대기 노드에는 운영 노드를 찌를
주소(상호 프로브), 다음 보고까지의 간격. 그룹에 속하지 않은 시스템은 `assigned: false`를 받고
계속 보고한다(그룹에 편입되면 다음 보고에서 알게 된다). 서비스 정의를 전달하는 별도 경로가 없다.

#### 측정값은 배정과 짝지어 기록한다

보고는 자신이 따른 배정(`groupId`, `role`)을 되돌려 적는다. 그 그룹·역할이 노드의 **현재**
배정과 같을 때만 기록하고 판정한다. 배정을 아직 모르는 첫 보고나, 역할이 바뀐 직후 옛 역할로 잰
값은 새 역할의 기준으로 판정되면 안 되기 때문이다. 에이전트는 배정이 바뀌면 간격을 기다리지 않고
한 번 바로 다시 잰다(응답이 계속 바뀌어도 연속 재보고는 한 번만 한다).

#### 생존은 보고 수신 시각으로만 판단한다

`agents.last_seen_at`은 롱폴에서만 갱신되어 백업 중인 에이전트는 오프라인처럼 보인다. 이중화
판정은 헬스 보고 **수신 시각**만 쓰고, 보고 루프는 잡 루프와 별도 고루틴에서 돈다. 보고가 끊긴
노드는 보고가 오지 않으므로, 서버가 `AIHA_FRAMEWORK_HA_REPORT_INTERVAL`마다 모든 그룹을 스스로
평가한다(`runHAEvaluator`).

#### 보고는 시스템을 지정하지 않는다

인벤토리와 같다: 본문에 `systemId`가 없고, 대상은 에이전트 토큰으로 결정한다(설계서 그림 5-1의
예시와 다른 점, ha-roadmap 4절 항목 15). 본문으로 시스템을 고를 수 있으면 유효한 토큰 하나로 죽은
운영 노드를 살아 있는 것처럼 보이게 할 수 있다. 보고에는 상태 값만 담고 설정 원문과 공유 비밀은
담지 않는다.

#### 판정과 기록

판정 규칙(설계서 표 5-1, 5-3)과 그룹 상태 전이(ha-roadmap 6절)는 `pkg/framework/ha/evaluate.go`의
순수 함수 `Assess`다. 보고 기록 → 판정 → 그룹 갱신 → 이벤트 기록은 **그룹 행 잠금 아래 한
트랜잭션**이다. 두 노드의 보고와 서버의 틱 평가가 순서대로 처리되고, 이벤트는 그룹별 순번
(`ha_groups.event_seq`)을 받아 순번 순서가 곧 커밋 순서가 된다(ha-roadmap 4절 항목 17).

| 조건 | 판정 |
| --- | --- |
| 운영 보고 끊김(`AIHA_FRAMEWORK_HA_STALE_AFTER` 초과), 운영 서비스·포트·헬스 API 실패 | error |
| 양쪽 Primary, 역할 불일치, 복제 상태 미보고·조회 실패, 디스크 `Inconsistent`·`Outdated` 등 | error |
| 복제 연결 끊김: 유예(`STALE_AFTER`) 이내 attention, 넘으면 error | attention / error |
| 재동기화 진행, 미동기량 > 0 또는 미보고, 대기 보고 지연, 대기 서비스 실행 중, GPU 부족, 헬스 API 지연 초과, 상호 프로브 실패 | attention |

"마지막 동기화 확인 시각"은 양쪽이 `Connected`·`UpToDate`이고 미동기량을 **0으로 보고**한 마지막
평가 시각이다. 미동기량을 읽지 못하면 확인으로 치지 않는다.

**복제 상태**는 에이전트가 DRBD 9의 `drbdsetup status --json <리소스>`로 읽는다(`pkg/agent/ha/drbd`,
2026-11-12). H0 실측([ha-h0.md](ha-h0.md))에서 정한 형식이며, 사람이 읽는 텍스트 출력은 쓰지 않는다.

- 보고 필드는 DRBD의 어휘 그대로다: `role`·`peerRole`, `connection`(연결 상태), `sync`(DRBD 9의
  replication 상태 — `Established`, `SyncSource`, `SyncTarget`, `Off` …), `disk`·`peerDisk`.
- `outOfSyncBytes`는 DRBD가 KiB로 세는 `out-of-sync`를 바이트로 바꾼 값이다. 출력에 없으면 생략한다.
- 리소스·볼륨·연결이 각각 하나가 아니거나 필수 필드가 비면 일부만 읽지 않고 `error`에 사유를 담는다.
  프레임워크는 이를 "복제 상태 조회 실패"(error)로 판정한다. DRBD 8.4 노드도 같은 경로로 실패가 드러난다.
- split-brain은 상태 출력에 `StandAlone`으로만 나타나고 사유는 커널 로그에만 남는다. 지금은 연결 끊김으로
  판정되며, 구별은 H4 재합류에서 한다(ha-roadmap 4절 항목 18).

## 3. 잡 상태머신

### 3.1 백업 잡

```
  queued ──claim──> claimed ──시작보고──> running ──┬──> completed
    │                  │                    │      │
    │                  │                    │      └──> failed
    │                  └── 리스 만료 ────────┘
    │                     (claimed는 queued 복귀,
    │                      running은 프로토타입에선 failed)
    ├── 취소 ──> cancelling ──> cancelled
    └── 취소(대기중) ──> cancelled
```

| 상태 | 의미 | 타임아웃 | 만료 시 전이 |
| --- | --- | --- | --- |
| `queued` | 큐에서 에이전트를 기다림 | 잡 유효기간 (예: 24h) | `failed` (사유: 에이전트 미도달) |
| `claimed` | 점유했으나 아직 시작 안 함 | 짧게 (예: 5m) | `queued` (아직 쓰기 시작 전이므로 안전). 그 전에 잡 유효기간이 지나면 `failed` (사유: 유효기간 안에 시작 안 함) — 시도도 함께 닫는다 |
| `running` | 수행 중 | 리스 만료 | **프로토타입: `failed`** (결과 미확인). 2.2절 정책 완비 후 재실행 허용 |
| `cancelling` | 취소 요청됨, 중단 확인 대기 | 리스 만료 | `failed` (사유: 중단 미확인) |
| `completed` / `failed` / `cancelled` | 종료 | — | — |

`claimed`와 `running`의 만료 처리가 다른 이유: `claimed`는 아직 저장소에 아무것도
쓰지 않았으므로 되돌려도 안전하지만, `running`은 옛 시도가 계속 쓰고 있을 수 있다.

유효기간이 지난 `claimed`는 큐로 되돌려도 다시 claim될 수 없으므로 끝낸다. 2026-11-25까지는 어느 정리에도
걸리지 않아 `claimed`로 남았고, 끝나지 않은 잡으로 세어져 흐름 시작을 막고 그 잡을 기다리는 이중화 흐름을 멈춰
두었다. 이중화 잡은 유효기간(5m)과 `claimed` 대기 시간(5m)이 같아, claim한 에이전트가 시작 보고 전에 죽으면
항상 이렇게 되었다. 잡과 시도는 한 문장에서 잡 행을 먼저 잠그고(`job_id` 순) 함께 닫는다.

진행 보고는 잡 행을 잠근 한 트랜잭션에서 처리한다(잡 → 시도 순서, 스위퍼·흐름 종료와 같다). 잡의 현재 시도가
이 시도이고, 잡이 `running`·`cancelling`이거나 유효기간 안의 `claimed`일 때만 보고를 반영하고, 첫 보고면 같은
트랜잭션에서 `running`으로 옮긴다. 그 밖은 리스 무효로 거절한다. **유효기간은 시작 마감이다** — 스위퍼가 돌기
전이라도 만료된 잡은 시작하지 않는다. 따로 처리하던 때는 보고가 시도에 반영된 뒤 잡이 끝나거나 다른 시도에
넘어가도 시작으로 응답할 수 있었다.

### 3.2 복구 잡

```
  queued ──> provisioning ──> awaiting_agent ──> claimed ──> restoring ──> awaiting_boot ──> completed
     │            │                 │               │            │               │
     └── 취소     └─ 실패            └─ 타임아웃       └─ 타임아웃    └─ 실패/두절      └─ 타임아웃
```

| 상태 | 의미 | 타임아웃 | 만료 시 |
| --- | --- | --- | --- |
| `queued` | 복구 잡 생성, 플랜 수립 완료 | 잡 유효기간 | `failed` |
| `provisioning` | 인프라 API로 인스턴스 생성 요청 중 | 예: 10m | `failed` (인스턴스 생성 실패) |
| `awaiting_agent` | 부팅 + 레스큐 진입 + 에이전트 콜백 대기 | 예: 30m | `failed` (복구 환경 준비 실패) |
| `claimed` | 레스큐 에이전트가 claim함. 응답이 도착했는지, 복구가 시작됐는지는 아직 모름. 같은 요청 키는 재수신 기한(기본 10m) 동안 같은 응답을 다시 받는다. 첫 `progress`에 `restoring`으로 | 복구 시작 보고 대기 (**미구현** — 스위퍼 없음) | `failed` (복구 미시작). 예기치 않은 재부팅은 `grub-reboot`이 1회성이라 원래 OS로 부팅되므로 이어받지 않는다 |
| `restoring` | 에이전트가 복구 수행 중. `result`가 `succeeded`면 `awaiting_boot`, `failed`면 `failed`(`preparing` 실패는 `claimed`로 복귀) | 리스 만료 (**미구현** — 지금은 `last_progress_at`만 기록) | 아래 참조. **자동 재시도 없음** |
| `awaiting_boot` | 복구된 OS 부팅 및 확인 대기 | 예: 30m | 아래 참조 |
| `completed` / `failed` / `cancelled` | 종료 | — | — |

**현재 구현**: `queued`·`provisioning`이 없다 — 인스턴스를 수동으로 만들므로 `restore create`가
곧바로 `awaiting_agent`로 만든다. `awaiting_boot`에서 멈추며(boot-verify 없음), 복구 잡에는 타임아웃 스위퍼가 없다 —
`awaiting_agent`의 claim 기한은 늦은 claim을 거절할 뿐 상태를 바꾸지 않는다.

`awaiting_agent`와 `awaiting_boot`에 타임아웃이 필수인 이유: VM이 레스큐로 뜨지
않거나(grub 설정 실패, 이미지 다운로드 실패) 복구된 OS가 부팅에 실패하면 콜백이 영영
오지 않는다. 타임아웃이 없으면 잡이 영구 대기하고 사용자는 아무 상태도 보지 못한다.

#### 실행 결과와 확인 결과의 분리

**리스 만료로 연락이 끊긴 것은 복구 실패가 확인된 것이 아니다.** 잡의 최종 상태와
별개로 아래 두 필드를 남겨야 "복구 실패"와 "확인 불가"를 구분할 수 있다.

| 상황 | `restoreOutcome` | `bootVerification` |
| --- | --- | --- |
| 에이전트가 복구 오류 보고 | `failed` | `n/a` |
| 복구 중 통신 두절 | `unknown` | `n/a` |
| 디스크 복구 성공, 부팅 확인 대기 | `succeeded` | `pending` |
| 부팅 확인 완료 | `succeeded` | `verified` |
| 부팅 확인 시간 초과 | `succeeded` | `timed_out` |

`restoreOutcome=unknown`은 사용자에게 특히 중요하다. 디스크가 이미 포맷되었을 수
있으므로 "실패했으니 다시 시도하세요"와는 다른 안내가 필요하다.

`bootVerification=timed_out`일 때 잡을 `failed`로 볼지 별도 종결 상태로 볼지는
[open-decisions.md](open-decisions.md) 3번과 함께 정한다.

#### 부팅 확인의 인증

복구된 OS의 부팅 확인을 **일반 에이전트의 온라인 전환으로 판정해서는 안 된다.**
복구된 OS는 백업 이미지에서 온 것이라 **원본 시스템의 `systemId`와 자격증명 사본을
그대로 갖는다.** 원본 VM이 아직 살아 있으면 둘을 구분할 수 없다.

해결: **복구 플랜이 복구된 디스크에 1회용 부팅 확인 토큰을 심는다.**
[Restore.md](Restore.md) 복구 절차 10번이 이미 "복구ID를 포함한 JSON 파일을 복구한 OS
디스크에 저장"하므로, 그 파일을 운반체로 삼아 복구ID와 **별개인** 부팅 확인 토큰을
함께 기록한다. 부팅한 OS의 에이전트가 그 토큰으로 `boot-verify`를 호출하면, 그것은
"원본 시스템의 자격증명을 가진 무언가"가 아니라 **"이 복구 잡이 만든 디스크로 부팅한
주체"** 임이 증명된다.

원본 시스템 · 복구 대상 인스턴스 · 복구 후 에이전트의 식별 관계는
[data-model.md](data-model.md) 3.1과 [open-decisions.md](open-decisions.md) 3번에서
정한다.

### 3.3 잡 종류 확장

이력 스키마는 잡 종류(`backup` / `restore`)를 필드로 구분한다. SFR-HA-07(2029)이
이중화·전환 이력과의 통합 관리를 요구하고, 마이그레이션 협력 방식에 따라
`migration` 잡 종류가 추가될 수 있기 때문이다
([architecture.md](architecture.md) 5.2).

### 3.4 이중화 잡 (2026-11-13 구현, [ha-roadmap.md](ha-roadmap.md) H3a)

잡 큐가 백업 외 종류를 싣는다. 이중화 잡은 이중화 작업 흐름(H3b부터)만 만들고, 흐름의 한 단계·한
노드에 잡 하나다. 상태머신은 3.1절과 같고, 아래만 다르다.

| 항목 | 내용 |
| --- | --- |
| 종류 | `replication-setup`, `replication-teardown`, `ha-demote`, `ha-promote`(설계서 표 4-6), `ha-rejoin`(로드맵 4절 항목 1). 스키마 제약 `jobs_kind_check`가 Go의 `Kind` 상수와 같은 목록을 허용한다 |
| 유효기간 | 백업 `AIHA_FRAMEWORK_JOB_TTL`(24h), 이중화 `AIHA_FRAMEWORK_HA_JOB_TTL`(5m). 이중화 잡은 지켜보는 작업의 한 단계여서 오래 기다린 잡은 이미 바뀐 상태에 작용한다 |
| claim 응답 | `kind`가 추가된다. 백업은 `repository`, 이중화 잡은 그 단계에 필요할 때 `replication.sharedSecret`. 둘 다 claim 기록 **전에** 복호화하고, 실패하면 아무것도 바뀌지 않아 같은 claim을 다시 할 수 있다(2.5절 규칙 유지). 해당 없는 쪽은 응답에 없다 |
| 흐름 확인 | 잡 명세의 흐름 ID·단계를 흐름이 판단한다(`job.Flows`. `job`은 `ha`를 import하지 않는다). claim 때 `Admit`, 시작 보고(`claimed` 상태의 첫 진행 보고) 때 `Current`를 묻는다 |
| 흐름이 진행된 잡 | 409로 거절하고 **잡을 `failed`로 끝낸다.** claim 뒤라면 시도도 `failed`로 닫아 이후 보고를 거절한다. 큐에 남기면 롱폴마다 다시 내려가 에이전트가 같은 잡을 계속 claim한다. 흐름을 조회하지 못한 것은 거절일 뿐 상태를 바꾸지 않는다 |
| 시작 이후 보고 | 흐름을 다시 묻지 않는다. 에이전트는 시작 보고가 승인되기 전에는 아무것도 하지 않으므로 늦게 도착한 잡은 시작 보고에서 걸러진다. 그 뒤에 보고를 거절하면 승격·강등 도중에 멈추게 되어 단계를 끝내고 흐름이 결과를 판단하는 것보다 나쁘다 |
| 백업 생성 | 진행 중인 흐름에 속한 시스템이면 거절(409). 흐름이 서비스를 멈추거나 데이터를 옮기는 중이다 |
| 취소 | 이중화 잡은 거절(409, 2.6절) |
| 에이전트 | 종류마다 실행기 하나(`worker.New`의 `runners`). 실행기가 없는 종류는 claim한 뒤 **시작 보고 없이** `failed` 결과를 보낸다(`This agent does not run "<kind>" jobs: upgrade it`). 시작 전 잡의 결과는 프레임워크가 받는다 |
| 흐름 트랜잭션 | `job.InsertTx`로 흐름의 단계 전진과 그 단계의 잡 생성을 한 트랜잭션에 묶는다 |
| 마이그레이션 | `Migrate`는 명령마다 돈다. `jobs_kind_check`가 없거나 모든 종류를 담지 않을 때만 교체한다. 첫 릴리스의 표(`backup`만 허용)에 반복 적용해도 행이 유지되고, 정의되지 않은 종류는 계속 거절된다(PostgreSQL 테스트) |

H3a 시점의 서버는 흐름 없이 돌았다(`Flows`가 nil). H3b(2026-11-16)부터 서버와 잡을 다루는 CLI 명령 모두
`ha.FlowService`를 연결한다. 흐름에 속하지 않은 이중화 잡은 "흐름이 진행된 잡"과 같이 claim에서 거절하고
끝낸다.

알려진 한계: 흐름 확인(`Current`)과 잡의 시작 전이는 한 트랜잭션이 아니다. 흐름 종료가 시작 전 잡을 먼저
끝내면(`RejectTx`, 잡 행 잠금) 뒤의 시작 보고는 거절된다(2026-11-25, 3.1절). 반대로 시작이 먼저 확정되면 그
잡은 흐름이 끝난 뒤에도 끝까지 간다 — 시작 이후에는 흐름을 다시 묻지 않는다는 위 규칙 그대로다. 그 잡이 끝날
때까지는 흐름 시작과 `ha acknowledge`가 "끝나지 않은 잡"으로 거절된다. 백업 생성의 흐름 확인과, 흐름 시작 시의
대기·실행 중 잡 확인도 한 트랜잭션이 아니다 — 확인 직후 다른 쪽이 시작되면 둘이 함께 진행될 수 있다.
운영자 명령끼리의 짧은 경합이어서 프로토타입에서는 받아들인다. 필요해지면 시스템별 advisory lock으로 두
경로를 묶는다.

### 3.5 이중화 작업 흐름 — 복제 구성·해제 (2026-11-16 구현, [ha-roadmap.md](ha-roadmap.md) H3b)

흐름은 그룹 하나에 대한 작업을 **단계별 잡**으로 수행한다. 한 단계는 한 노드의 잡 하나다.

| 흐름 | 1단계 | 2단계 | 그룹 상태 |
| --- | --- | --- | --- |
| `setup` (`ha setup`) | 대기 노드 `replication-setup` | 운영 노드 `replication-setup`(`initialPrimary`) | `registered` → `configuring` → 완료 시 `syncing`. 평가기가 동기화·서비스 정상을 보고 `protected`로 옮긴다 |
| `teardown` (`ha teardown`) | 운영 노드 `replication-teardown` | 대기 노드 `replication-teardown` | `registered`·`syncing`·`protected`·`degraded` → `configuring` → 완료 시 `registered` |

규칙:

| 항목 | 내용 |
| --- | --- |
| 하나씩 | 그룹당 진행 중인 흐름은 하나(`ha_flows` 부분 유니크 인덱스). 두 노드 중 어느 쪽에든 끝나지 않은 잡이 있으면 흐름을 시작하지 않는다(종류 무관). 두 노드 모두 `AIHA_FRAMEWORK_HA_STALE_AFTER` 안에 보고했어야 한다 — 리소스 파일의 `on` 절에 넣을 호스트명이 보고에서 온다 |
| 한 트랜잭션 | 흐름 기록·단계 전진·그 단계의 잡 생성·그룹 상태 전이·이벤트는 그룹 행 잠금 아래 한 트랜잭션이다. `ha_flow_jobs`의 키 `(흐름, 단계, 시스템)`이 재시작 뒤 같은 단계의 재발행을 막는다 |
| 다음 단계 | 서버 주기 루프(`runHAEvaluator`, 보고 주기마다)가 진행한다. 단계의 잡이 `completed`이고, **잡이 끝난 뒤 받은 그 노드의 헬스 보고가 결과를 뒷받침할 때만** 다음 잡을 만든다. 대기 구성은 리소스가 `Secondary`로, 운영 구성은 `Primary`로, 해제는 리소스가 없어진 것(상태 조회 실패)으로 확인한다 |
| 멈춤 | 잡이 `failed`·`cancelled`이거나, `completed`인데 `AIHA_FRAMEWORK_HA_STALE_AFTER` 안에 보고가 뒷받침하지 않으면 흐름은 `failed`, 그룹은 `error`. 흐름의 시작 전 잡은 같은 트랜잭션에서 끝낸다. 자동 재시도는 없다 |
| 확인(`ha acknowledge`) | `error`에서만. 그룹 시스템의 끝나지 않은 이중화 잡이 있거나, 대기 노드가 최신 보고에서 `Primary`이면 거절. 마지막 흐름이 실패였으면 `registered`(구성·해제를 다시 요청할 수 있다), 아니면 `degraded`(평가기가 판단) |
| 재요청 | 실패한 구성을 확인 후 다시 요청하면 1단계부터 다시 나간다. 각 노드는 이미 된 단계를 건너뛴다(아래 표). 공유 비밀은 그룹당 한 번 만들어 유지하므로 다시 써도 리소스 파일이 바뀌지 않는다 |

잡 명세는 비밀을 담지 않는다(`model.ReplicationSetupSpec`, `ReplicationTeardownSpec`). 흐름 ID·단계, 리소스
이름, 복제 장치, 마운트 지점, 포트, 프로토콜(`C`), 서비스 유닛, 자기·상대 노드(호스트명, 주소, 노드 ID, 데이터
디스크 `by-id` 경로), `initialPrimary`, 운영 노드에는 대기 노드가 잰 디스크 크기(`peerDiskBytes`)가 들어간다.
운영 노드의 명세는 대기 노드의 명세를 뒤집어 만든다 — 두 노드의 리소스 파일이 같아야 한다. 노드 ID는 역할이
아니라 시스템에 묶인다(그룹 등록 때 운영 0, 대기 1). 공유 비밀은 `AIHA_FRAMEWORK_SECRET_KEY_FILE`의 키로
봉인해 그룹에 두고(AAD `ha-group:<groupId>`), 구성 잡의 claim 응답(`replication.sharedSecret`)으로만 나간다.

잡 결과의 `detail`은 `model.ReplicationJobResult`다: 단계 목록(`name`, 이번에 했으면 `done: true`, 이미
되어 있었으면 `false`), 데이터 디스크 크기, 끝났을 때의 역할·디스크 상태. 실패해도 그때까지의 단계를 싣는다.

에이전트 실행기(`pkg/agent/ha/replication`)의 단계와 건너뛰는 조건:

| 단계 | 하는 일 | 건너뛰는 조건 / 거절 |
| --- | --- | --- |
| 실행 전 검사 | 호스트명이 명세와 같은지, 데이터 디스크(`by-id` 링크)가 전체 디스크이고 파티션·마운트가 없는지, `blkid -p` 서명이 없거나 `drbd`인지, 서명이 없으면 앞뒤 1 MiB가 0인지(`cmp`, 명세의 `overwriteDisk`가 있으면 0이 아니어도 진행), 상대 디스크와 크기가 같은지, `drbd@<리소스>.target`이 있는지, `drbd.service`가 enable 되어 있지 않은지, 서비스 유닛이 있고 다른 유닛이 기동하지 않는지(`TriggeredBy`), 서비스가 정지 상태인지 | 하나라도 어긋나면 **아무것도 바꾸지 않고** 거절. 서비스 실행 중은 운영 노드가 이미 구성을 끝낸 상태(리소스 Primary, 마운트 활성)일 때만 허용 |
| 파일 | 리소스 파일(`0600`, DRBD 9 문법, `auto-promote no`, 노드 ID 순), 마운트 유닛(`[Install]` 없음), 서비스 드롭인(`RequiresMountsFor=`), `drbdadm dump`로 문법 확인 | 내용이 같으면 쓰지 않고 `daemon-reload`도 하지 않는다 |
| 서비스 부팅 기동 해제 | `systemctl disable` | 이미 disable |
| 메타데이터 | `drbdadm create-md` | 서명이 `drbd`면 생략. `--force`는 `overwriteDisk`로 데이터가 있는 디스크를 쓸 때만 붙이고, 그때 `overwrite-disk-data` 단계를 기록한다. `drbdmeta`는 처음 68 KiB가 0이 아니면 확인을 묻고, 잡에는 답할 사람이 없다 |
| 기동 | `systemctl enable drbd-configured.target drbd@<리소스>.target`, `systemctl start drbd@<리소스>.target`(PID 1이 모듈 적재·`adjust`), `drbdadm adjust`. 유닛 인스턴스는 systemd 이스케이프한 리소스 이름이다(`-` → `\x2d`). `drbd@.service`가 풀린 이름을 `drbdadm`에 넘기므로, 이스케이프하지 않으면 `-`가 `/`가 되어 다른 리소스의 볼륨으로 읽힌다 | 이미 떠 있으면 `adjust`만 적용 |
| (운영) 승격 | 상대 연결을 최대 2분 기다린 뒤, 양쪽 `Inconsistent`면 `primary --force`(첫 승격), 자기 `UpToDate`면 `primary` | 이미 Primary면 생략. 그 밖의 디스크 상태는 거절 |
| (운영) 포맷 | `mkfs.ext4 -q -E nodiscard` | 복제 장치에 ext4가 있으면 생략. 다른 서명은 거절 |
| (운영) 마운트·서비스 | `systemctl start <마운트 유닛>`, `systemctl start <서비스>` 후 `active` 확인 | 이미 활성이면 생략 |
| 해제 | 서비스 정지 → 언마운트 → (Primary면) `drbdsetup secondary` → `drbd@<리소스>.target` disable·정지 → 남아 있으면 `drbdsetup down` → 리소스 파일·마운트 유닛·드롭인 제거 | 각 단계가 이미 그렇다면 생략. **데이터와 메타데이터는 지우지 않는다** |

`drbd.service`는 쓰지 않는다(설치 기본값이 disabled이고 그대로 둔다). 기동 스크립트가 모든 리소스의 상대
연결을 기다리고(`wait-con-int`), 대기 시간 기본값이 무제한이어서, 상대보다 먼저 구성되는 대기 노드에서는 기동이 끝나지 않고, 부팅 때에도 상대가 꺼져
있으면 같다. LINBIT도 유닛 설명에서 리소스별 `drbd@.target`을 쓰라고 한다([ha-roadmap.md](ha-roadmap.md)
7절 결정 7).

**스키마 적용과 잠금.** `Migrate`는 명령마다 돌고 스크립트 전체가 한 트랜잭션이다. `CREATE INDEX IF NOT
EXISTS`와 `ALTER TABLE … IF NOT EXISTS`는 할 일이 없어도 표를 먼저 잠그므로, 서버의 claim·보고와 반대 순서로
잠금이 쌓여 교착이 났다(H3b 테스트에서 재현: 잡 스키마가 `jobs`를 잡고 `attempts`를 기다리는 동안 claim이
반대로 기다림). 모든 스키마(잡, HA, 에이전트, 복구)에서 기존 표를 바꾸는 문장을 카탈로그 확인 뒤에만 실행하도록
바꿨다. 새 스키마나 열을 더할 때도 같은 형태(`DO` 블록 안에서 `pg_attribute`·`to_regclass` 확인)로 쓴다. 최신
DB에서는 어떤 표 잠금도 기다리지 않는다 — `openDB`가 적용하는 목록 전체를, 모든 표에 쓰기 잠금을 건 트랜잭션
옆에서 `lock_timeout` 1초로 적용하는 테스트(`aiha-framework/cmd/migrate_test.go`)가 지킨다.

### 4.1 엔드포인트

2026-11-03에 라우트와 Swagger 계약을 모두 세웠다. **✅ 는 실제로 동작하고, 🚧 는 501
(`NOT_IMPLEMENTED`)을 답한다** — 클라이언트가 404 대신 "계약에는 있으나 아직 없음"을 알 수 있게
자리를 둔다. 계약의 정본은 `pkg/api/rest/docs/swagger.json`이고, 등록된 라우트와 문서가 어긋나면
`TestSwaggerMatchesTheRoutes`가 실패한다.

`AIHA_FRAMEWORK_ADMIN_TOKEN_FILE`이 없으면 이 절의 라우트(`readyz`, `swagger.json` 제외)는 열리지
않는다 (4.7절).

**보호 대상 (HA-09: 백업 대상 현황 파악 / 구성 도출)**

| 메서드 | 경로 | 용도 | 상태 |
| --- | --- | --- | --- |
| GET | `/aiha/systems` | 보호 대상 시스템 목록, 에이전트 상태, `lastSeenAt` | ✅ |
| GET | `/aiha/systems/{systemId}` | 시스템 상세, 인벤토리 요약 | ✅ |
| GET | `/aiha/systems/{systemId}/inventory` | 에이전트가 보고한 구성 정보 + **수집 시각** | ✅ |
| POST | `/aiha/systems/{systemId}/inventory/refresh` | 구성 재수집 요청 (비동기) | 🚧 |
| PUT | `/aiha/systems/{systemId}/targets` | 백업 대상 구성 등록 | 🚧 |

시스템은 별도 테이블 없이 **에이전트 등록에서 도출한다.** 재설치로 한 시스템에 에이전트가 여럿이면
온라인인 것, 폐기되지 않은 것, 최근 등록된 것 순으로 대표를 고른다.

구성 정보는 프레임워크가 조회하는 것이 아니라 **에이전트가 보고**한 것이므로
(`POST /aiha/agent/inventory`), 항상 수집 시각과 함께 제공한다. 오래된 구성 정보로
백업 대상을 정하면 이미 사라진 파티션을 지정할 수 있다.

**백업 (HA-09: 백업 실행 / 결과 검증)**

| 메서드 | 경로 | 용도 | 상태 |
| --- | --- | --- | --- |
| POST | `/aiha/systems/{systemId}/backups` | 백업 요청 → 잡 생성 (비동기) | ✅ |
| GET | `/aiha/backups` | 전 시스템 백업 이력 (필터: 시스템, 기간, 상태) | ✅ |
| GET | `/aiha/backups/{backupSetId}` | 백업본 상세 (크기, 결과, 오류) | ✅ |
| DELETE | `/aiha/backups/{backupSetId}` | 백업본 삭제 | 🚧 |

`/aiha/backups`는 별도 카탈로그가 아니라 **백업 잡과 그 시도에서 읽는다.** 그래서 실패한 잡도
이력에 나오고, 세트를 만들기 전에 실패했으면 `backupSetId`가 없다. 프레임워크는 매니페스트를 읽지
않으므로 크기는 세트 단위 업로드 바이트(`processedBytes`)와 항목 수(`items`)뿐이고, 파티션별 크기는
없다. 저장소에 파일이 아직 있는지도 알지 못한다.

### 4.2 비동기 요청 규약

백업·복구 요청은 즉시 완료되지 않는다.

- **`202 Accepted`** 를 반환하고 본문에 `jobId`를 담는다.
- `Location` 헤더로 상태 조회 위치를 알려준다.
- 완료를 기다리는 동기 응답은 제공하지 않는다. 포털은 상태 조회로 폴링한다.
- 낡은 인벤토리처럼 요청을 막지는 않지만 알려야 할 것은 응답의 `warnings`에 담는다.

`restoreId`와 `recoveryId`의 관계를 명시한다. 둘은 **별개**로 둔다.

| ID | 성격 | 노출 범위 |
| --- | --- | --- |
| `restoreId` | 복구 잡의 식별자 | 북향 (포털·사용자) |
| `recoveryId` | 레스큐 환경에 주입되는 식별자 | 남향 (user-data 경유) |

분리하는 이유: `recoveryId`는 EC2 user-data를 통해 인스턴스 안의 모든 프로세스가
읽을 수 있다([Restore.md](Restore.md) 5절). 사용자에게 노출되는 잡 ID와 동일하게
두면, 포털에서 본 ID로 남향 엔드포인트를 시도할 수 있는 관계가 만들어진다.

**현재 구현의 예외**: `InfraProvisioner`가 없어 인스턴스를 사람이 만들므로, `POST /aiha/restores`
응답의 `rescue` 객체가 `recoveryId`·`claimToken`·프레임워크 접속 정보를 **이 응답에서 한 번만**
돌려준다(`restore create`의 출력과 같다). 조회 응답에는 없고, `GET /aiha/restores/{id}`는
`restoreId`로만 찾는다. 프로비저닝이 들어오면 `rescue`를 없앤다.

### 4.3 멱등성

**생성 계열 요청은 `Idempotency-Key` 헤더를 받는다.** 포털의 POST 재시도로 잡이나
**실제 VM이 두 개 생성되는 것**을 막아야 하기 때문이다. 복구는 인프라를 실제로
프로비저닝하므로 특히 중요하다.

| 엔드포인트 | 멱등성 |
| --- | --- |
| `POST /aiha/systems/{systemId}/backups` | `Idempotency-Key` 필수 |
| `POST /aiha/restores` | `Idempotency-Key` **필수** |
| `POST /aiha/repositories` | `Idempotency-Key` 권장 |
| `POST .../cancel` | 본질적으로 멱등 (이미 취소면 200) |
| `DELETE /aiha/backups/{id}` | 본질적으로 멱등 (없으면 204 또는 404 일관 처리) |

동일 키·동일 내용의 재요청에는 기존 `jobId`를 반환하고, 동일 키·다른 내용이면 409로
거부한다.

**아직 구현하지 않았다**([roadmap.md](roadmap.md) 3.2). 지금은 재시도하면 잡이 하나 더 생기며,
Swagger 설명에 이 점을 밝혀 두었다. 복구는 claim 토큰을 해시로만 보관하므로 재요청에 같은 토큰을
돌려줄 수 없어, 구현할 때 응답 규약을 함께 정해야 한다. 인스턴스 자동 생성이 들어오기 전에 필요하다.

### 4.4 진행률 표현

진행률을 단일 백분율로 내리지 않는다. 아카이브 전체 크기를 미리 알 수 없는 경우가
많기 때문이다(파티션을 스트리밍하며 압축하므로 최종 크기는 완료 전까지 미확정).

| 필드 | 의미 |
| --- | --- |
| `status` | 잡 상태 (3절의 상태머신) |
| `phase` | 세부 단계 (예: `mounting`, `archiving`, `uploading`, `finalizing`) |
| `processedBytes` | 처리한 양 |
| `totalBytes` | 전체 양 (추정치일 수 있음) |
| `totalUnknown` | `totalBytes`를 확정할 수 없으면 `true` |
| `lastProgressAt` | 마지막으로 처리량·단계가 변한 시각 |

`totalUnknown=true`일 때 포털은 백분율 대신 처리량과 경과 시간을 표시한다. 백업 잡은 항상
`true`이고(`totalBytes` 없음), 복구는 레스큐 에이전트가 전체 크기를 보고한 뒤로 `false`다.

### 4.5 오류 표현

**표시 메시지와 기계 판독용 오류 코드를 구분한다.**

- 표시 메시지: CLAUDE.md의 [API Response Messages] 규칙. 호출자 관점으로 쓰고,
  내부 라이브러리·파서·검증기의 `err.Error()`를 그대로 넣지 않는다. 장기 실행 작업은
  소요 시간을 포함한다(`"Backup completed (2m14s)"`).
- 오류 코드: 안정적인 문자열 상수(예: `AGENT_OFFLINE`, `REPOSITORY_UNREACHABLE`,
  `LEASE_EXPIRED`, `RESTORE_OUTCOME_UNKNOWN`). 포털과 상위 자동화가 분기 판단에 쓴다.

`model.SimpleMsg`에 선택 필드 `code`를 두어 표현한다(2026-11-03). 메시지만 쓰는 남향 응답과
호환되고, CLAUDE.md의 핸들러 패턴을 유지한다. 관리 API가 직접 답하는 실패에는 항상 `code`가 있고,
값은 `pkg/api/rest/model/model.go`의 `Code*` 상수다. 레이트 리밋(429)처럼 라우트에 닿기 전에
끊긴 요청에는 없다. AI-MCMP 공통 규약이 정해지면 다시 맞춘다
([open-decisions.md](open-decisions.md) 10번).

**절대 노출하지 않는 것**: 저장소 자격증명, DB 연결 문자열, 내부 스택 트레이스.

### 4.6 저장소 검증의 주체

**프레임워크에서 저장소 접속에 성공해도, 고객 VPC 안의 에이전트에서 접속 가능하다는
보장은 없다.** VPC 엔드포인트, 라우팅, 보안그룹, 프록시, IAM 인스턴스 프로파일이
모두 다르다.

따라서 `POST /aiha/repositories/{repoId}/verify`는 **검증 주체를 명시적으로 받는다.**

| 주체 | 확인하는 것 |
| --- | --- |
| `framework` | 프레임워크가 저장소 메타데이터를 읽을 수 있는지 |
| `agent:{systemId}` | **해당 에이전트가 실제로 백업을 쓸 수 있는지** (검증 잡을 큐에 넣어 수행) |

실제 백업 성공 여부를 예측하는 것은 후자뿐이다. 전자만으로 "검증 완료"라고 표시하면
잘못된 안심을 준다.

### 4.7 인증

방식은 [open-decisions.md](open-decisions.md) 8번에서 **확정했다**(2026-09-17).
요약하면, 자격을 네 종류로 나누고 용도를 섞지 않는다.

| 자격 | 용도 | 권한·수명 |
| --- | --- | --- |
| **북향 관리용 자격** | 운영자·포털이 프레임워크 API 호출 | 허용된 관리 작업만 |
| **등록 토큰** | 백업 에이전트 최초 등록 | 등록만 허용. 예: 30분·1회 |
| **에이전트 토큰** | 등록 후 잡 수신·진행률·결과 보고 | 그 에이전트에 배정된 작업만 |
| **복구용 claim token** | 레스큐/부팅확인 단계 | 지정된 `recoveryId` 한정, 짧은 TTL·1회 |
| 복구 보고 토큰 (`reportToken`) | 레스큐의 progress·result | claim 응답마다 새로 발급, 마지막 것만 유효 (2026-10-08) |

**등록 토큰으로 백업 명령을 내리거나, 에이전트 토큰으로 다른 에이전트를 등록할 수
없어야 한다.** 북향의 Keycloak SSO + RBAC(SFR-API-03, 2027년 베스핀글로벌 담당)은
통합 *사용자* 인증이므로, 그것이 들어와도 에이전트 등록과 개별 자격 관리는 별도로
남는다.

**`systemId`·`agentId`는 식별자이지 인증 수단이 아니다.** 클라이언트가 기존
`systemId`를 보냈다는 이유로 그 시스템에 연결해 주면 안 된다. 연결 대상은 등록
토큰에 부여된 권한으로 결정한다. 마찬가지로 토큰 검증만으로는 부족하다 — 토큰으로
`agentId`를 정한 뒤, **그 작업이 해당 에이전트에 배정된 것인지 다시 검사한다.**

**북향 관리용 자격(2026-11-03 구현)**: `AIHA_FRAMEWORK_ADMIN_TOKEN_FILE`의 토큰을
`Authorization: Bearer`로 보낸다. 서버는 해시만 메모리에 두고 상수 시간으로 비교한다. 미설정이면
관리 API를 열지 않는다 — 인증 없는 모드는 없다. 미들웨어가 호출 주체(`Principal`)를 구성하고 검증
함수는 주입받으므로, Keycloak으로 바꿀 때 `rest.StaticAdminToken`만 교체하면 핸들러는 그대로다.
호출 주체는 잡의 `requested_by`에 남는다. 역할 구분(TM-AI-HA-04의 조회·제어 실행 등)은 아직 없고
토큰 소지자는 모든 관리 작업을 할 수 있다.

에이전트 토큰은 JWT나 인증서가 아니라 `crypto/rand` 32바이트 Bearer 토큰이고,
프레임워크 DB에는 SHA-256 해시만 저장한다(`pkg/framework/token`). 상세와 회전 정책은 [open-decisions.md](open-decisions.md)
8번.

### 4.8 재시도와 부하 제어

에이전트와 포털 양쪽 모두에 적용한다.

- 프레임워크는 과부하 시 **429**를 반환하고 `Retry-After`를 붙인다.
- 일시적 5xx도 재시도 대상이다. 지수 백오프 + jitter를 적용한다.
- **정상 롱폴 `wait` 타임아웃(204)은 재시도가 아니라 정상 흐름**이므로 백오프하지
  않는다. 이를 혼동하면 에이전트가 점점 느리게 폴링하게 된다.
- 재시도해서는 안 되는 오류(400, 401, 403, 409)를 명확히 구분한다.

## 5. 로깅

CLAUDE.md의 [Logging] 규칙을 따른다. 남향/북향 양쪽에서 아래 필드를 일관되게 붙인다.

| 필드 | 대상 |
| --- | --- |
| `systemId` | 보호 대상 시스템 |
| `jobId` | 논리적 작업 |
| `attemptId` | 실행 시도 |
| `backupSetId` | 백업본 |
| `restoreId` | 복구 잡 |
| `agentId` | 에이전트 |

`attemptId`를 반드시 함께 남긴다. 중복 실행이 의심되는 상황을 로그만으로 판별하려면
어느 시도의 로그인지 구분되어야 한다.

**절대 로그에 남기지 않는 것**: 저장소 자격증명(액세스 키, 시크릿, 세션 토큰, SSH 키,
SMB 비밀번호), 복구 클레임 토큰, 부팅 확인 토큰, bootstrap 자격, 자격증명이 포함된
저장소 URI.

특히 복구 경로는 저장소 접속 정보를 에이전트에 중개하므로, 요청/응답 본문을 통째로
로깅하는 미들웨어가 이 엔드포인트에 걸리지 않도록 주의한다. 현재
`pkg/api/rest/server.go`의 `requestLogger()`는 메서드·URI·상태·지연만 기록하고
본문을 남기지 않으므로 이 성질을 유지한다.
